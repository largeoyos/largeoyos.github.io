## CUDA 编程入门:第四节 —— GPU 内存层次

### 一、先抛一个让你不安的事实

到目前为止,你写的代码"能跑"。但我现在告诉你:**上一节那个向量加法,理论上跑得有多快,你知道吗?**

向量加法这个操作,对每个元素做了 1 次加法(1 个 FLOP),但读了 2 个 float、写了 1 个 float(共 12 字节)。算术强度 = `1 / 12 ≈ 0.083 FLOP/byte`。

现代 GPU 计算能力可以到 ~30 TFLOPS,显存带宽 ~1 TB/s。意思是:**这个 kernel 不可能受计算限制,它一定受内存带宽限制**——GPU 99% 的时间在等数据从显存搬过来,计算单元几乎是闲的。

> **这是 GPU 编程最反直觉的事实之一:大多数实际 kernel 不是被"算得不够快"卡住,而是被"数据搬不过来"卡住。**

所以如果你要让程序更快,关键不在写更聪明的算法,而在**搞清楚数据是怎么在 GPU 内部流动的,并尽可能减少昂贵的内存访问**。这就是这一节的主题。

### 二、GPU 内存层次:一张你必须装进脑子的图

GPU 上不止"一种"内存。它是分层的,从慢到快、从大到小:

```
┌──────────────────────────────────────────────────────────┐
│  Host Memory (CPU 主内存)        ~100 GB    ~50 GB/s     │  ← 通过 PCIe 拷贝
├──────────────────────────────────────────────────────────┤
│  Global Memory (全局显存)        ~24 GB     ~1 TB/s      │  ← cudaMalloc 给你的
│  Constant Memory (常量内存)      64 KB      带缓存       │
│  Texture Memory (纹理内存)       —          带缓存       │
├──────────────────────────────────────────────────────────┤
│  L2 Cache                        几 MB      ~3 TB/s      │  ← GPU 自动管理
├──────────────────────────────────────────────────────────┤
│  Shared Memory (共享内存)        ~100 KB/SM ~10 TB/s     │  ← 你显式管理
│  L1 Cache                        和 shared 同一块物理      │
├──────────────────────────────────────────────────────────┤
│  Registers (寄存器)              ~256 KB/SM 最快         │  ← 编译器自动用
└──────────────────────────────────────────────────────────┘
```

你在 `cudaMalloc` 拿到的指针,都指向 **Global Memory**。这就是为什么向量加法是带宽受限的——它每次都从这层"最大但最慢"的存储读数据。

我们入门阶段重点关心三层,从下到上:

#### 1. 寄存器(Registers)

每个线程有自己的寄存器。你在核函数里写的局部变量:

```c
__global__ void foo(...) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    float tmp = 0.0f;     // 这些都在寄存器里
}
```

这些 `i`、`tmp` 编译器会尽量放在寄存器里。访问速度近乎免费(1 周期),但**容量有限**——每个 SM 总共 ~256 KB 寄存器,被该 SM 上所有正在运行的线程瓜分。如果你一个线程用了太多寄存器,SM 上能并发的线程数就会减少(这叫 **occupancy 下降**),反而拖慢整体。我们后面会再提。

#### 2. 共享内存(Shared Memory)

这是 CUDA 编程的"灵魂特性"。**同一个 Block 内的所有线程共享一块快速内存**——这就是上一节我提的"Block 内可以协作"的物理基础。

它有几个关键性质:

- **作用域是一个 Block**:Block 0 的 shared memory 和 Block 1 的 shared memory 是不同的两块,互相看不见
- **生命周期是核函数执行期间**:核函数结束就没了
- **速度比 global memory 快约 100 倍**(延迟 ~30 周期 vs ~500 周期)
- **容量小**:每个 SM 大约 100 KB 上下,且要被该 SM 上所有 Block 瓜分
- **必须显式声明和管理**:编译器不会自动帮你用,要你自己写代码

声明语法:

```c
__shared__ float tile[256];
```

`__shared__` 关键字,放在核函数内部的局部变量前。

#### 3. 全局内存(Global Memory)

`cudaMalloc` 给你的就是这个。容量大(GB 级),所有线程都能读写,但**慢**——这是性能瓶颈的常见来源。

### 三、共享内存的核心用法:数据复用

什么时候用 shared memory?**当你发现同一份数据被一个 Block 内多个线程反复读**的时候。

来,我用一个具体例子让你感受到这件事。考虑一个简单问题:**1D 滑动窗口求和**,每个元素的输出是它自己 + 左右各一个邻居的和:

```
output[i] = input[i-1] + input[i] + input[i+1]
```

如果直接写,每个线程读 3 次 global memory:

```c
__global__ void stencil_naive(const float* in, float* out, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= 1 && i < N - 1) {
        out[i] = in[i-1] + in[i] + in[i+1];
    }
```

注意——`in[5]` 这个值,会被线程 4(读 `in[4+1]`)、线程 5(读 `in[5]`)、线程 6(读 `in[6-1]`)**总共 3 个线程**各从 global memory 读一次。**同一份数据被读了 3 次**,每次都走那条慢路。能不能让它只从 global memory 读一次,然后大家在快速内存里共享?

**能,这就是 shared memory 的典型套路**:

```c
__global__ void stencil_shared(const float* in, float* out, int N) {
    __shared__ float tile[256 + 2];   // Block 大小 256,左右各加 1 个"光环"

    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int tid = threadIdx.x;

    // 步骤 1:每个线程合作把数据从 global 搬到 shared
    if (i < N) tile[tid + 1] = in[i];
    if (tid == 0 && i > 0)            tile[0]   = in[i - 1];
    if (tid == 255 && i < N - 1)      tile[257] = in[i + 1];

    // 步骤 2:等所有线程都搬完了,再开始算
    __syncthreads();

    // 步骤 3:从 shared 读数据计算
    if (i >= 1 && i < N - 1) {
        out[i] = tile[tid] + tile[tid + 1] + tile[tid + 2];
    }
```

这段代码引入了**两个新东西**,我们一个一个看。

#### `__syncthreads()` —— Block 内同步屏障

这个函数让**当前 Block 内**所有线程在这里集合,等所有线程都到达这一行,才一起往下走。

为什么需要它?——你想想:线程 0 把 `tile[1] = in[0]` 写完了,正准备读 `tile[2]`。但 `tile[2]` 是线程 1 负责写的,线程 1 可能还没跑到那一步!如果没有同步,线程 0 读到的就是垃圾值。

`__syncthreads()` 是 Block 级别的栅栏。**注意三件事**:

1. **它只同步同一个 Block 内的线程**,不能跨 Block 同步(跨 Block 同步需要核函数结束/重启)
2. **必须让 Block 内所有线程都执行到这一行**——如果有线程在 `if` 里跳过了它,而另一些线程在等它,**死锁**
3. 这就是为什么 Block 是"协作单位"——`__syncthreads` 是协作的关键工具

#### 数据搬运的"协作模式"

注意 shared memory 是怎么填的:**每个线程负责搬运一小部分,合起来填满整个 tile**。这是 CUDA 里非常常见的模式,你以后会反复见到:

```
搬运阶段(每个线程搬一点)→ __syncthreads() → 计算阶段(每个线程读多个)
```

它的根本好处:**N 个线程,N 次 global memory 读,但每个线程在 shared memory 里读了 3 次。把 3N 次慢读变成了 N 次慢读 + 3N 次快读。**

### 四、还有一个不能忽略的概念:合并访问(Coalescing)

即使你只用 global memory,**怎么访问它**也极大影响性能。这一点说完这一节就结束了,但**它和 shared memory 同样重要**。

GPU 读 global memory 时,**是一次读一大块**(通常 32 字节或 128 字节为一组)。如果一个 warp(32 个连续线程)访问的是连续地址:

```
线程 0  → A[0]
线程 1  → A[1]
...
线程 31 → A[31]
```

那 GPU 一次读取 128 字节就把 32 个线程都喂饱了。这叫 **合并访问(coalesced access)**,是最优情况。

但如果 32 个线程访问的是**跳跃**的地址:

```
线程 0  → A[0]
线程 1  → A[100]
线程 2  → A[200]
...
```

GPU 只能一次一个去读,带宽利用率掉到 1/32。

**写 CUDA 代码的一条潜规则**:让 `threadIdx.x` 紧挨着的相邻线程访问紧挨着的内存地址。再回头看你写的向量加法:

```c
int i = blockIdx.x * blockDim.x + threadIdx.x;
C[i] = A[i] + B[i];
```

线程 0 访问 `A[0]`,线程 1 访问 `A[1]`……**完美合并**。这是为什么 `i = blockIdx.x * blockDim.x + threadIdx.x` 这个公式是这个顺序,而不是反过来——它天然保证了合并访问。

### 五、本节的关键认知升级

如果你只能从这一节带走两件事,我希望是:

1. **大多数 CUDA kernel 是被内存带宽卡死的,不是被计算卡死的。** 优化 = 减少 global memory 访问次数 + 让访问尽量合并。
2. **Shared memory 是 GPU 给你的"手动管理的缓存"**,核心用法是"每个 Block 把一块数据从 global 搬到 shared,Block 内多个线程共享使用,减少重复读"。配合 `__syncthreads()` 协调。

## CUDA 编程入门:第五节 —— Warp、SM 与执行模型

前四节讲的是"软件层面"的抽象:线程、Block、Grid、共享内存。但你写的代码最终要在硬件上跑。**这一节讲硬件,讲完之后你会理解很多之前"为什么是这样设计"的问题。**

### 一、先问你一个问题

到目前为止,你脑子里 GPU 上线程的执行模型大概是这样的:

> "我启动了 256 × 1000 个线程,GPU 把它们分配到核心上,每个线程独立跑自己的代码。"

这个模型**大致**对,但有一个关键的细节是错的。我们来揭开它。

### 二、Warp:32 个线程的"绑定关系"

GPU 硬件上,**线程不是一个一个独立调度的,而是 32 个一组打包调度的**。这 32 个线程叫一个 **warp**(中文有时翻译成"线程束")。

具体来说:**一个 Block 内的线程,按 `threadIdx` 顺序每 32 个组成一个 warp**。比如 Block 大小是 256,那这个 Block 就有 256/32 = 8 个 warp:

```
Warp 0: 线程   0 ~ 31
Warp 1: 线程  32 ~ 63
Warp 2: 线程  64 ~ 95
...
Warp 7: 线程 224 ~ 255
```

**关键事实**:同一个 warp 里的 32 个线程,**在硬件上是同步执行的**——它们共享一个指令发射单元,**每个时钟周期执行同一条指令**。

> 这就是 SIMT(Single Instruction, Multiple Threads)的"SI"——Single Instruction。32 个线程在同一时刻执行**同一条指令**,只是各自的数据不同。

**第一个停顿点** 🛑

回想第 4 节我说的"合并访问":一个 warp(32 个连续线程)访问连续地址时,GPU 一次读一大块就喂饱所有线程。**现在你应该能理解为什么是 32 这个数字了**——它就是一个 warp 的大小。warp 是硬件读内存的"批发单位"。

(如果你这里没"啊哈"一下,停一下,再读一遍上一段。)

### 三、Warp Divergence:if-else 的隐藏成本

既然一个 warp 里 32 个线程必须执行同一条指令,那这段代码会发生什么?

```c
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i % 2 == 0) {
    // 路径 A:做一堆事
    foo(i);
} else {
    // 路径 B:做另一堆事
    bar(i);
}
```

一个 warp 里 32 个线程,有 16 个走 A 分支,16 个走 B 分支。但硬件只能发一条指令——**怎么办?**

答案是:**warp 会分两次跑**。

1. 先执行 A 分支:走 A 的 16 个线程正常算,走 B 的 16 个线程**被禁用,空跑**
2. 再执行 B 分支:走 B 的 16 个线程正常算,走 A 的 16 个线程被禁用

总耗时约等于 A + B 的时间。这种现象叫 **warp divergence(线程束分化)**。

**这是 CUDA 写代码的一条潜规则**:同一 warp 内尽量走相同的分支。

但请注意——**不是所有 if 都会导致 divergence**。回到第 3 节你写过的:

```c
if (i < N) {
    C[i] = A[i] + B[i];
}
```

这个 if 大部分 warp 里**所有 32 个线程的判断结果是一样的**(都满足 `i < N`),只有最后一个 warp 可能少数线程不满足。所以代价微乎其微。**真正昂贵的是 warp 内不同线程走向不同分支**。

**第二个停顿点** 🛑

回头看第 4 节第 1 题(那段 buggy 代码):

```c
if (tid < 128) {
    __syncthreads();   // ← 这里
    ...
}
```

我提示过"想想 `__syncthreads` 的硬性规定"。现在你有了 warp 的视角,能更深地理解这个 bug 吗?

`__syncthreads()` 要求 **Block 内所有线程都到达**才能放行。但 `tid >= 128` 的那 128 个线程根本不会进 if 体,永远到不了 `__syncthreads`,于是 `tid < 128` 的那些线程**永久等待**——**死锁**。

**铁律**:`__syncthreads()` 必须放在所有线程都会执行的位置,**绝不能放在分支里**(除非你能保证 Block 内所有线程都走同一条分支)。

### 四、SM:warp 的栖息地

现在我们再往硬件里走一层。

GPU 由若干个 **SM(Streaming Multiprocessor,流式多处理器)** 组成。一颗 RTX 4090 有 128 个 SM,A100 有 108 个 SM。**SM 是 GPU 真正干活的"小处理器"**。

每个 SM 有:

- 一堆 CUDA 核心(执行算术运算)
- 几个 warp 调度器(决定下一周期跑哪个 warp)
- 一块寄存器文件(被该 SM 上所有线程瓜分)
- 一块 shared memory / L1 cache(被该 SM 上所有 Block 瓜分)

**Block 怎么分配到 SM?**

当你启动 `<<<1000, 256>>>`,这 1000 个 Block 不是平均分给 SM,而是**按需调度**:

1. GPU 把 Block 一个一个塞给 SM
2. 一个 SM 同时能容纳多少个 Block,取决于资源够不够(寄存器、shared memory)
3. 一个 Block 一旦分配给某个 SM,就**在那个 SM 上跑到结束**——不会迁移
4. SM 上的活干完了,GPU 再塞下一个 Block 给它

**这就是为什么 Block 之间不能互相同步**——它们可能在不同 SM 上跑,可能不同时存在(有的还没开始,有的已经结束)。Block 间通信只能靠核函数结束、CPU 介入、再启动下一个核函数。

**第三个停顿点** 🛑

我现在能告诉你第 4 节第 2 题的答案了。两段代码:

```c
// 版本 A:sum += A[j * N + i]
// 版本 B:sum += A[i * 100 + j]
```

在内层循环 `j` 的某次迭代里,看看一个 warp 内相邻线程(`i` 相差 1)访问的地址:

- **A**:`A[j*N + 0]`、`A[j*N + 1]`、`A[j*N + 2]`…… 相邻线程访问相邻地址 → **合并访问** ✓
- **B**:`A[0*100 + j]`、`A[1*100 + j]`、`A[2*100 + j]`…… 相邻线程访问间隔 100 个 float → **每个线程触发一次单独的内存事务** ✗

A 比 B 快约 **30 倍**。这是初学者最容易写出的"看起来一样但性能天差地别"的代码。

> 写 CUDA 代码时,**永远问自己**:"我让 `threadIdx.x` 是循环的内层还是外层?它对应的是连续的内存吗?"

### 五、Occupancy:为什么 GPU 喜欢"超额订阅"

这里有件事可能让你困惑:**SM 上同时驻留的线程,其实远多于硬件能"并行"执行的数目**。

比如一个 SM 可能只有 128 个 CUDA 核心,但它会**同时驻留**几十个 warp(上千个线程)。为什么?

因为**等待**。当一个 warp 发起一次 global memory 读取,要等几百个周期数据才回来。如果 SM 只有这一个 warp,这几百个周期就闲着。但如果 SM 上有几十个 warp,**warp 调度器立刻切换到另一个 warp**接着跑,数据回来了再切回来。

**这是 GPU 隐藏延迟的核心机制**:不是让单个 warp 跑得更快,而是**让足够多的 warp 来回切换,把内存等待时间填满**。

> CPU 隐藏延迟靠**缓存**(避免延迟),GPU 隐藏延迟靠**并发**(用别的工作填满延迟)。这是两种处理器的设计哲学差异在硬件层面的体现。

所以:

- 一个 SM 上同时驻留的 warp / 最大可驻留数 = **occupancy(占用率)**
- Occupancy 不需要 100%,但太低会导致 SM 没足够 warp 来回切,延迟暴露
- **占用率被什么限制?**——每个 SM 的资源是固定的:寄存器、shared memory、最大线程数。如果你的 kernel 用太多寄存器或 shared memory,**单个 Block 占资源大,SM 上能塞下的 Block 就少,occupancy 下降**

举个具体感觉:假设一个 SM 寄存器总量 65536 个,如果你的 kernel 每个线程用 32 个寄存器,Block 大小 256,那:

- 每个 Block 占 32 × 256 = 8192 个寄存器
- 一个 SM 能塞 65536 / 8192 = 8 个 Block

但如果你写得太复杂,每个线程用了 128 个寄存器:

- 每个 Block 占 128 × 256 = 32768 个寄存器
- 一个 SM 只能塞 2 个 Block —— **occupancy 减半**

**初学者不必死磕 occupancy**,但你要知道有这件事:**写 kernel 时让单线程别太"胖"**。

### 六、把所有概念串起来

现在你有了完整图景。让我们用一张"自下而上"的图把所有东西串起来:

```
你的代码                        硬件
─────────────────────────────────────────────────
启动 kernel <<<grid, block>>>
   │
   ↓
Grid (一堆 Block)        →   被塞给 GPU
   │
   ↓
Block (一堆线程)         →   被分配给某个 SM,在那里跑到结束
   │
   ↓
Warp (32 个连续线程)     →   SM 调度的最小单位,锁步执行
   │
   ↓
Thread (单个线程)        →   有自己的寄存器,执行自己的数据
```

每一层都对应一个硬件/性能概念:

|软件层|硬件对应|性能含义|
|---|---|---|
|Grid|整个 GPU|总工作量|
|Block|SM|资源分配单位、协作单位|
|Warp|调度单位|divergence、合并访问的"32"|
|Thread|CUDA core 上的执行流|寄存器使用|

// 方案 A

### 第 1 题:warp divergence 判断

- **(a) `threadIdx.x < 16`**:**严重 divergence**。Warp 0 包含线程 0~31,其中 0~15 走 if,16~31 走 else,**同一 warp 内分裂**。
- **(b) `blockIdx.x < 16`**:**没有 divergence**。同一个 Block 内所有线程的 `blockIdx.x` 相同,整个 Block(及其所有 warp)走同一条分支。
- **(c) `threadIdx.x % 2 == 0`**:**最坏的 divergence**。Warp 内偶数线程和奇数线程交错,32 个线程分裂成两组,各跑一半时间。
- **(d) `data[threadIdx.x] > 0`**:**取决于数据**。如果数据规律(比如前一半正后一半负),warp 内可能一致;如果数据随机,严重 divergence。**这是最隐蔽的一种**——代码看起来没问题,性能却不可预测。

### 第 2 题:2D 图像映射

**方案 A 更好**。

关键事实是:**CUDA 把 2D Block 内的线程按 `threadIdx.x` 变化最快的顺序打包成 warp**。也就是说,一个 16×16 的 Block(共 256 线程,8 个 warp),warp 0 是 `(threadIdx.x, threadIdx.y) = (0~15, 0)` 加上 `(0~15, 1)` 的前一半……简化说:**`threadIdx.x` 相邻的线程在同一个 warp 里**。

- **方案 A**:`threadIdx.x` 相邻 → `x` 相邻 → `img[y*W + x]` 地址相邻 → **合并访问** ✓
- **方案 B**:`threadIdx.x` 相邻 → `y` 相邻 → 地址间隔 W → **跨行跳跃,完全不合并** ✗

> 一条易记的规则:**让 `threadIdx.x` 永远对应你内存里"变化最快"的维度**(C 语言数组的最右维度)。

### 第 3 题:Grid-stride 风格的向量加法

很多人第一反应会写"一个线程处理连续的 4 个元素":

```c
// ✗ 不推荐写法
for (int k = 0; k < 4; k++) {
    int idx = i * 4 + k;
    C[idx] = A[idx] + B[idx];
}
```

这样写**warp 内一次访问的地址是不连续的**——线程 0 在 k=0 时访问 `A[0]`,线程 1 同时访问 `A[4]`,间隔了 4 个 float,**合并访问被破坏**。

正确写法是让线程访问**间隔 blockDim.x × gridDim.x** 的元素:

```c
__global__ void vectorAdd_v3(const float* A, const float* B, float* C, int N) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;   // 整个 Grid 的总线程数

    for (int i = tid; i < N; i += stride) {
        C[i] = A[i] + B[i];
    }
```

每次循环迭代里,warp 内 32 个连续线程访问 `A[tid]`、`A[tid+1]`、`A[tid+2]`……**完美合并**。下一次迭代,大家一起跳 `stride` 个元素再来一遍。

**这种写法叫 grid-stride loop**,有三个巨大好处:

1. **始终保持合并访问**
2. **解耦 Grid 大小和数据大小**——你可以启动比"刚好够"少的 Block 数(比如启动够填满 GPU 的就行),让每个线程多干几次。Grid 启动开销变小,occupancy 调控更灵活。
3. **代码对任意 N 都能工作**,不用算 `(N + 255) / 256` 这种向上取整,核函数自己处理。

记住这个模式——**它是真实生产代码里 90% 的 CUDA kernel 写法**。
