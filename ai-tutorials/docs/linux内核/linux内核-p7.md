## 第十三节：系统调用机制——用户态与内核态切换的完整实现

前十二节我们一直在内核里"游览"，看进程如何调度、内存如何管理、文件如何读写。但有一个问题我们始终没有正面回答：用户程序是怎么"进入"内核的？当你的C程序调用 `read(fd, buf, len)` 时，这个调用是怎么越过用户态和内核态之间那道严格的特权边界的？这一节我们把这扇"门"完整地打开，从 `syscall` 指令的执行一直追踪到内核函数的调用，再到结果返回用户程序。

理解系统调用机制有一个特别的价值：它是你所有用户程序和内核交互的唯一通道。无论你写的是网络服务器、数据库、游戏引擎，只要涉及I/O、内存、进程操作，最终都要走这扇门。理解了它，你对"程序在运行时到底发生了什么"的认识会提升一个层次。

---

### 13.1 为什么需要系统调用：重温特权级的意义

我们在第一节提到过特权级，这里在系统调用的语境下重新建立一次更清晰的认识。

x86-64 CPU把执行环境分成四个特权级（ring 0到ring 3），Linux只用了两个：ring 0（内核态）和ring 3（用户态）。在ring 3里运行的代码有严格限制：不能执行特权指令（比如直接修改CR3页表寄存器、直接操作I/O端口），不能访问内核地址空间的内存（MMU会拒绝并触发缺页异常）。这两条限制共同保证了用户程序无法直接操控硬件、无法读取其他进程的内存。

但用户程序必然需要访问硬件资源——读文件、发网络包、分配内存。唯一合法的途径就是请求内核代劳：用户程序发出一个"我需要做某件事"的请求，内核验证请求的合法性，以自己的特权完成实际操作，把结果还给用户程序。这个"发出请求——内核处理——返回结果"的完整过程，就是一次系统调用。

关键的约束是：这个从ring 3到ring 0的转换，**不能让用户程序自由地跳到内核任意地址执行**，否则用户程序只需要构造一个"跳到内核里修改其他进程内存"的系统调用就能完全绕过隔离。所以这个转换必须通过一个受控的入口点，内核预先定义好哪些功能可以被请求、入口在哪里、参数如何传递。

---

### 13.2 系统调用表：内核功能的目录

Linux用一张**系统调用表**来定义所有可以被用户程序请求的内核操作。每个系统调用对应一个编号，用户程序把编号放入 `rax` 寄存器，内核根据编号查表找到对应的处理函数：

```c
// arch/x86/entry/syscalls/syscall_64.tbl（片段）
// 格式：编号  ABI类型  名字  对应的内核函数
0    common  read                sys_read
1    common  write               sys_write
2    common  open                sys_open
3    common  close               sys_close
9    common  mmap                sys_mmap
11   common  munmap              sys_munmap
39   common  getpid              sys_getpid
57   common  fork                sys_fork
59   common  execve              sys_execve
60   common  exit                sys_exit
// ... 目前Linux x86-64共有约340个系统调用
```

这张表在编译时被处理成一个函数指针数组 `sys_call_table`，存在内核的只读数据段里（防止被恶意模块修改）。系统调用号就是这个数组的下标，`sys_call_table[0]` 是 `sys_read`，`sys_call_table[1]` 是 `sys_write`，以此类推。

你可能注意到这些函数名以 `sys_` 开头，但如果你去内核源码里搜索，会发现用 `SYSCALL_DEFINE` 宏定义的函数名里没有 `sys_` 前缀。这是因为 `SYSCALL_DEFINE` 宏在展开时自动加上了前缀，同时还做了参数类型检查和安全相关的包装。这个宏是Linux内核代码里一个设计相当精巧的元编程技巧：

```c
// include/linux/syscalls.h
// SYSCALL_DEFINE3 表示有3个参数的系统调用
// 这个宏展开后生成真正的系统调用函数，自动添加 sys_ 前缀
// 并包含参数类型安全检查的包装代码

// 以 read 系统调用为例
SYSCALL_DEFINE3(read,           // 函数名（展开后是 sys_read）
    unsigned int, fd,           // 第一个参数：文件描述符
    char __user *, buf,         // 第二个参数：用户空间缓冲区
                                // __user 标注告诉编译器和静态分析工具
                                // 这个指针指向用户空间，不能直接解引用
    size_t, count)              // 第三个参数：读取字节数
{
    struct fd f = fdget_pos(fd);
    // ... 实际的 read 逻辑，第六节已经讲过
}
```

`__user` 标注是内核代码里一个很有意思的设计。它不影响编译结果，纯粹是给静态分析工具（特别是 `sparse`）看的注解。如果一个函数接收了 `__user` 指针却直接解引用（而不是用 `copy_from_user`），`sparse` 会发出警告。这是一种用类型系统来防止安全漏洞（用户空间指针未经验证直接使用）的方法，在大型代码库里非常有价值。

### 13.3 `syscall` 指令：硬件层面的特权级切换

用户程序怎么触发这个转换？在x86-64上，专门设计了一条 `syscall` 指令用于这个目的。你的C程序调用 `read()` 时，glibc里的 `read` 函数包装了这条指令：

asm

```asm
# glibc 里 read() 的汇编实现（x86-64）
# 文件：sysdeps/unix/sysv/linux/x86_64/syscall.S
.globl read
read:
    mov    $0, %rax      # 把系统调用号0（read）放入 rax 寄存器
    mov    %rdi, %rdi    # 第一个参数 fd 已经在 rdi 里（调用约定）
    mov    %rsi, %rsi    # 第二个参数 buf 已经在 rsi 里
    mov    %rdx, %rdx    # 第三个参数 count 已经在 rdx 里
    syscall              # 触发系统调用！
    # syscall 返回后，rax 里存放的是返回值（或错误码的负数）
    ret
```

`syscall` 指令在硬件层面做了以下几件事，全部由CPU自动完成，不需要任何软件参与。首先它把当前的 `rip`（下一条要执行的指令地址）和 `rflags`（标志寄存器）保存到两个专用的MSR寄存器（`IA32_LSTAR` 附近的寄存器）里，以便系统调用返回时恢复执行位置。然后它把 `cs`（代码段寄存器）切换到内核代码段，这一步实现了从ring 3到ring 0的特权级切换。最后它把 `rip` 设置为预先存在 `IA32_LSTAR` MSR里的地址，也就是内核系统调用入口函数的地址。

注意 `syscall` 指令**没有切换栈**——此时CPU还在用用户程序的栈。栈的切换是接下来内核入口汇编代码手动完成的。这个设计是故意的：`syscall` 指令本身要尽可能快，把复杂的工作留给软件处理。

### 13.4 内核入口汇编：`entry_SYSCALL_64`

`IA32_LSTAR` MSR里存储的地址指向 `entry_SYSCALL_64` 函数，它在 `arch/x86/entry/entry_64.S` 里用汇编写成。这是整个系统调用机制里最"底层"的部分，也是最值得仔细阅读的部分，因为它揭示了用户态到内核态切换时CPU状态的每一个细节：

asm

```asm
/* arch/x86/entry/entry_64.S（核心部分，加了注释） */
SYM_CODE_START(entry_SYSCALL_64):

    /* 此时我们在 ring 0，但还在用用户态的栈！
       第一件事：切换到内核栈
       swapgs 指令交换 gs 基址寄存器和 IA32_KERNEL_GS_BASE MSR 的值
       内核在 MSR 里预存了当前进程的 task_struct 地址
       swapgs 之后，gs 指向 task_struct，就能访问内核的 per-CPU 数据 */
    swapgs

    /* 把用户态的栈指针（rsp）临时保存到 per-CPU 的 scratch space */
    movq    %rsp, PER_CPU_VAR(cpu_tss_rw + TSS_sp2)

    /* 从 TSS（任务状态段）里读取为这个进程预设的内核栈地址
       内核栈在 fork() 时分配，地址存在 task_struct 里
       再存入 TSS 的 sp1 字段，让这里能快速读取 */
    movq    PER_CPU_VAR(cpu_current_top_of_stack), %rsp

    /* 现在 rsp 指向内核栈了！接下来的 push 操作都在内核栈上 */

    /* 构建 pt_regs 结构体：把所有用户态寄存器压栈保存
       pt_regs 是内核保存被打断时 CPU 状态的标准结构体
       中断处理、系统调用、异常处理，都用这个结构体保存现场 */
    pushq   $__USER_DS                  /* ss：用户数据段 */
    pushq   PER_CPU_VAR(cpu_tss_rw + TSS_sp2) /* rsp：用户栈指针 */
    pushq   %r11                        /* rflags（syscall 指令把原 rflags 存到 r11）*/
    pushq   $__USER_CS                  /* cs：用户代码段 */
    pushq   %rcx                        /* rip（syscall 指令把返回地址存到 rcx）*/

    /* 保存其余的通用寄存器 */
    pushq   %rax    /* 系统调用号 */
    PUSH_AND_CLEAR_REGS rax=$-ENOSYS    /* 保存其他寄存器，顺便初始化返回值为"不支持" */

    /* 到这里，内核栈上已经有了一个完整的 pt_regs 结构体
       rsp 指向这个结构体的起始地址
       接下来跳转到 C 语言写的系统调用分发函数 */

    movq    %rsp, %rdi  /* 把 pt_regs 指针作为第一个参数传给 C 函数 */
    call    do_syscall_64
    /* do_syscall_64 返回后继续 */

    /* 恢复用户态寄存器，执行 sysretq 返回用户态 */
    POP_REGS
    sysretq /* 返回用户空间，ring 3，从 rcx 里保存的地址继续执行 */

SYM_CODE_END(entry_SYSCALL_64)
```

这段汇编代码里有两个细节特别值得你停下来思考。第一个是 `swapgs` 指令的作用。内核需要通过 `gs` 寄存器来访问当前CPU的 per-CPU 数据（包括内核栈地址），但在用户空间运行时，`gs` 可能被用户程序用于其他目的（比如glibc用它来访问线程本地存储）。`swapgs` 指令原子地交换 `gs` 基址和一个专用MSR的值，让内核进入时立刻能用 `gs` 访问内核数据，退出时再换回用户程序的 `gs` 值，两者互不干扰。

第二个是 `pt_regs` 结构体的构建。每次系统调用（以及中断、异常）进入内核时，内核都会把用户态所有寄存器的值压入内核栈，形成 `pt_regs` 结构体。这个结构体一方面保存了"返回用户空间时需要恢复的状态"，另一方面也让系统调用处理函数可以检查和修改用户程序的寄存器值——`ptrace`（调试器使用的接口）就是通过读写目标进程的 `pt_regs` 来实现"查看和修改被调试程序的寄存器"的。

### 13.5 `do_syscall_64`：从汇编进入C语言世界

`do_syscall_64` 是系统调用路径上第一个用C语言写的函数，它完成从"系统调用号"到"实际处理函数"的分发：

```c
// arch/x86/entry/common.c
__visible noinstr void do_syscall_64(struct pt_regs *regs, int nr)
{
    // 第一步：进入系统调用上下文
    // 这里做一些追踪和安全相关的工作（rcu_watch等）
    enter_from_user_mode(regs);

    // 第二步：处理系统调用追踪（strace 的底层原理在这里）
    // 如果进程设置了 TIF_SYSCALL_TRACE 标志（被 strace 跟踪），
    // 在执行系统调用之前先通知 tracer
    if (unlikely(regs->orig_ax != nr))
        nr = regs->orig_ax; // 允许 ptrace 修改系统调用号

    // 第三步：范围检查 + 查表调用
    // nr 就是用户程序放在 rax 里的系统调用号
    if (likely(nr < NR_syscalls)) {
        // sys_call_table 就是那张函数指针数组
        // nr 作为下标，找到对应的处理函数并调用
        // regs 里包含了所有参数（rdi, rsi, rdx, r10, r8, r9）
        regs->ax = sys_call_table[nr](regs);
    } else {
        // 系统调用号超出范围，返回 -ENOSYS（不支持的系统调用）
        regs->ax = -ENOSYS;
    }

    // 第四步：系统调用返回前的处理
    // 检查是否有信号需要递送、是否需要调度、是否有 ptrace 事件
    // 这是信号机制的触发点之一——信号不是立刻打断进程，
    // 而是在系统调用返回路径上被检查和递送的
    syscall_exit_to_user_mode(regs);
}
```

这段代码里有一个细节揭示了 `strace` 工具的工作原理，值得专门讲一下。当你用 `strace ls` 运行一个程序时，`strace` 通过 `ptrace(PTRACE_SYSCALL, ...)` 系统调用告诉内核"每次被追踪进程进入或退出系统调用时，请暂停它并通知我"。内核在 `do_syscall_64` 的入口和出口处检查 `TIF_SYSCALL_TRACE` 标志，如果设置了，就在这两个点暂停被追踪进程，切换到 `strace` 进程，让它读取 `pt_regs` 里的系统调用号和参数，打印出来，然后让被追踪进程继续。整个 `strace` 的功能，就建立在系统调用路径上的这两个"钩子"上。

### 13.6 参数是如何传递的：寄存器约定

用户程序调用 `read(fd, buf, count)` 时，这三个参数是如何传递给内核的 `sys_read` 函数的？这涉及一个叫做**系统调用约定（syscall calling convention）**的规范，它定义了参数放在哪个寄存器里：

```
x86-64 Linux 系统调用约定：
  rax = 系统调用号
  rdi = 第1个参数
  rsi = 第2个参数
  rdx = 第3个参数
  r10 = 第4个参数（注意：不是 rcx！rcx 被 syscall 指令用来保存 rip）
  r8  = 第5个参数
  r9  = 第6个参数

  系统调用最多6个参数（如果需要更多，通过指向结构体的指针传递）
  返回值放在 rax 里（负数表示错误，等于 -errno）
```

这个约定和普通函数调用的约定（System V AMD64 ABI）几乎相同，除了第4个参数用 `r10` 而不是 `rcx`。原因是 `syscall` 指令执行时会把返回地址（`rip`）存入 `rcx`，所以 `rcx` 不能用来传参数。

`sys_call_table` 里的函数接收的是 `struct pt_regs *regs`，然后从 `regs->di`、`regs->si`、`regs->dx` 等字段里取出参数。`SYSCALL_DEFINE` 宏展开后的代码自动完成这个解包过程，让最终的系统调用处理函数看起来像普通的C函数一样接收参数。

### 13.7 返回用户空间：`sysretq` 和信号的递送时机

`do_syscall_64` 返回后，汇编代码恢复寄存器，执行 `sysretq` 指令返回用户空间。`sysretq` 是 `syscall` 的逆操作：把 `rcx` 里保存的用户态 `rip` 恢复到 `rip`，把 `r11` 里保存的 `rflags` 恢复，把 `cs` 切换回用户代码段（ring 3），用户程序从 `syscall` 指令的下一条指令继续执行。

但在 `sysretq` 之前，`syscall_exit_to_user_mode()` 会做一系列检查，这里是整个内核里几个重要机制的汇合点。信号的递送就在这里发生：如果进程有待处理的信号（比如你按了Ctrl+C，内核给进程设置了 `SIGINT`），内核会在返回用户空间之前调用 `do_signal()`，构造一个信号处理帧压入用户栈，修改 `pt_regs` 里的 `rip` 指向用户注册的信号处理函数。这样当 `sysretq` 返回用户空间时，CPU不是回到原来的位置，而是跳进信号处理函数。信号处理函数执行完后，通过 `sigreturn` 系统调用恢复原来的执行上下文。这就是为什么信号的语义是"打断正在进行的系统调用，先处理信号"——因为信号递送发生在系统调用的返回路径上，而不是在系统调用执行过程中。

调度器的抢占检查同样在这里进行：如果 `TIF_NEED_RESCHED` 标志被设置（第四节讲过，时钟中断可能设置这个标志），内核在返回用户空间之前调用 `schedule()`，先完成一次进程切换。这就是用户态抢占的实现机制——当前进程不是在任意时刻被抢占的，而是在"从内核返回用户空间"这个自然的检查点被抢占的。

### 13.8 vDSO：让某些系统调用不需要进入内核

介绍完完整的系统调用流程之后，最后来看一个有趣的优化：**vDSO（virtual Dynamic Shared Object，虚拟动态共享对象）**。

系统调用的特权级切换有固定的开销，在现代CPU上大约是100-200纳秒。对于 `read`、`write` 这类必须进入内核的操作，这个开销是必要的。但有些系统调用，比如 `gettimeofday()`（获取当前时间），它只是读取一个内核维护的时间值，理论上不需要进入内核——如果内核能把这个时间值共享给用户空间直接读取，就能省掉整个切换开销。

vDSO正是这样工作的。内核在每个进程的地址空间里映射一小段内核代码和数据（通过 `mmap` 实现，进程不需要主动请求，内核在 `exec` 时自动映射）。这段代码实现了几个特定的系统调用（`gettimeofday`、`clock_gettime`、`getcpu` 等），直接在用户空间读取内核共享的时间数据，完全不需要 `syscall` 指令：

```c
// vDSO 里的 clock_gettime 实现（伪代码）
// 这段代码运行在用户空间（ring 3），但能安全地读取内核数据
int __vdso_clock_gettime(clockid_t clock, struct timespec *tp)
{
    // 直接读取内核通过共享内存暴露的时间数据
    // 这块内存是只读的（用户空间只有读权限），内核定期更新它
    struct vdso_data *vd = __arch_get_vdso_data();

    tp->tv_sec  = vd->wall_time_sec;
    tp->tv_nsec = vd->wall_time_nsec;
    // 不需要 syscall！这整个函数就是一个普通的函数调用
    return 0;
}
```

glibc的 `clock_gettime()` 会自动使用 vDSO 版本（如果可用），对调用者完全透明。在一个每秒调用 `clock_gettime` 数百万次的高性能程序里，vDSO带来的性能提升是非常显著的。你可以用 `cat /proc/self/maps | grep vdso` 来看你的进程里 vDSO 映射在哪个地址范围。

### 本节小结与思考练习

这一节我们完整追踪了一次系统调用的全程：用户程序把系统调用号和参数放入寄存器，执行 `syscall` 指令触发特权级切换，汇编入口 `entry_SYSCALL_64` 切换内核栈并保存用户态寄存器到 `pt_regs`，C函数 `do_syscall_64` 根据系统调用号查表调用处理函数，返回路径上检查信号和调度需求，最后 `sysretq` 恢复用户态执行。整条链路把硬件特权机制、内核数据结构、信号机制、调度器都自然地串联在了一起。

这里留一个非常值得深入的思考题，它把本节和第五节、第十节的知识联系在一起：我们说系统调用返回路径上会递送信号，信号处理函数在用户空间执行。信号处理函数执行完后，通过 `sigreturn` 系统调用恢复原来的执行上下文。但 `sigreturn` 是一个系统调用，它需要恢复原来的 `pt_regs`（包括原来的 `rip`、`rsp` 等）。这意味着 `sigreturn` 可以把 `rip` 设置成任意值。你能想到这个机制可能被如何滥用吗？内核有什么防御措施？（提示：搜索"return-oriented programming"和"signal frame hijacking"，以及内核的应对手段"shadow stack"和"PKRU"，你会触及现代CPU安全和操作系统安全之间一个非常深刻的交叉点。）

---

## 第十四节：内核性能分析——perf、ftrace与eBPF

前十三节我们建立了对内核各个子系统的深入理解。但理解原理和理解真实系统的运行状态之间，还有一段距离。一个内核函数在教科书上看起来很清晰，但在真实的服务器上，它每秒被调用多少次？花了多少时间？是哪些进程在调用它？在调用路径上有没有意想不到的热点？这些问题只有通过**性能分析工具**才能回答。

这一节我们来学习Linux内核自带的三套性能分析工具：`perf`、`ftrace` 和 `eBPF`。它们不只是工具，它们本身就是内核里精心设计的子系统，理解它们的实现原理，能让你对前几节讲的调度、中断、系统调用等机制有更立体的认识——因为这些工具正是通过"钩入"那些机制来工作的。

---

### 14.1 观察内核的根本挑战：如何测量不改变被测物

在讨论具体工具之前，先建立一个思维框架：对内核进行性能分析面临一个根本性的困难，叫做**观察者效应**。理想的性能分析工具应该能准确测量系统的行为，但测量本身会消耗CPU时间、改变缓存状态、增加中断频率，从而影响被测系统的行为。一个开销极大的追踪工具，测出来的结果反映的是"被追踪的系统"而不是"真实的系统"。

因此评价一个内核追踪工具，除了"能看到什么"，还必须考虑"开销是多少"。我们这一节讲的三套工具，在这个维度上有明显的梯度：`perf` 的采样方式开销最低（利用硬件性能计数器，每秒采样数百次，对系统影响极小）；`ftrace` 的函数追踪开销居中（需要在每个函数入口插入追踪代码）；`eBPF` 最灵活但也潜在地最重（取决于你写的程序做多少工作）。选择工具时，低开销应该是优先考虑的因素。

---

### 14.2 perf：硬件性能计数器的软件接口

`perf` 是Linux内核最主要的性能分析工具，它的核心是利用现代CPU内置的**硬件性能计数器（Hardware Performance Counters）**。每个现代CPU都有一组专用寄存器，能够计数各种硬件事件：指令执行数、缓存命中和缺失数、分支预测正确和错误数、TLB缺失数……这些计数器以极低的开销工作（本质上是硬件自己在数，不需要软件介入），当计数器溢出时触发一个性能监控中断（PMI），内核的 `perf` 子系统在中断处理程序里记录当前的 `rip`（程序计数器），这就是**采样**。

```bash
# perf 的几种典型用法，每种背后都有不同的内核机制

# 1. 统计系统范围的硬件事件（不采样，精确计数）
# 这里用的是 CPU 的 PMC（性能监控计数器）寄存器
perf stat -a sleep 5
# 输出示例：
#  10,234,567,890  instructions        # 5秒内执行了多少条指令
#   3,456,789,012  cache-references    # 多少次缓存访问
#     234,567,890  cache-misses        # 多少次缓存缺失（越高越差）
#   1,234,567,890  branch-misses       # 多少次分支预测错误

# 2. CPU 热点采样：哪些函数占用了最多 CPU 时间？
# 内核每 1ms（或按指令数）采样一次当前的调用栈
perf record -g -a sleep 10  # -g 表示记录调用栈，-a 表示全系统
perf report                  # 交互式查看结果

# 3. 追踪特定的内核事件（软件事件，不是硬件计数器）
# 比如统计每次 context switch（进程切换）时的调用栈
perf record -e sched:sched_switch -g -a sleep 5
```

`perf record` 生成的数据文件里存储了大量的采样点，每个采样点是一个 `(时间戳, PID, 调用栈)` 的三元组。`perf report` 把这些采样点按函数聚合，显示每个函数"在采样时出现在调用栈顶"的频率，这个频率近似于该函数占用CPU时间的比例。

理解 `perf` 的采样原理能帮你避免一个常见的误解：**采样分析看到的是"函数正在运行时被抓到的概率"，不是"函数被调用的次数"**。一个被调用百万次但每次只需1纳秒的函数，在采样结果里可能完全看不到；而一个只被调用一次但运行了1秒的函数，会占据采样结果的绝大部分。这是采样方法的天然特性，使用时需要有意识地考虑。

`perf` 在内核里有一个独立的子系统 `kernel/events/`，它定义了 `perf_event` 这个核心数据结构来描述一个监控事件，并通过 `perf_event_open()` 系统调用暴露给用户空间。当你创建一个 `perf_event` 时，内核根据事件类型（硬件计数器、软件事件、追踪点）选择对应的后端，编程CPU的PMC寄存器或注册软件钩子，采样数据通过内存映射的环形缓冲区传递给用户空间（`perf` 工具读取这个缓冲区），全程没有系统调用开销。

---

### 14.3 ftrace：函数级别的追踪框架

`perf` 的采样告诉你"时间花在哪里"，但它有一定的随机性，无法保证捕获每一次事件。如果你想精确地追踪"每次调用 `schedule()` 时都发生了什么"，需要一种不同的机制——`ftrace`（Function Tracer）。

`ftrace` 的核心思想是在编译内核时，用 `-mfentry` 编译选项让编译器在**每一个内核函数的入口处**插入一个对 `__fentry__` 的调用（一条 `call` 指令）。默认情况下，`__fentry__` 实际上是一个什么都不做的空函数（5字节的 `nop` 指令），几乎没有开销。当你开启某个追踪器时，内核**动态地把这些 `nop` 替换为真正的追踪代码**，这个技术叫做**动态代码修补（dynamic code patching）**。停止追踪时，再把代码改回 `nop`。

```bash
# ftrace 通过 /sys/kernel/debug/tracing/ 目录下的文件来控制
# 这正是第十一节讲的 sysfs 机制的应用

# 开启函数追踪器：追踪所有内核函数调用
echo function > /sys/kernel/debug/tracing/current_tracer
echo 1 > /sys/kernel/debug/tracing/tracing_on
sleep 1
echo 0 > /sys/kernel/debug/tracing/tracing_on

# 查看结果（格式：进程名-PID CPU# 时间戳 函数名）
cat /sys/kernel/debug/tracing/trace | head -50
# 输出示例：
#    bash-1234  [000] ....  1234.567890: schedule() {
#    bash-1234  [000] ....  1234.567891:   __schedule() {
#    bash-1234  [000] ....  1234.567892:     pick_next_task_fair()
#    bash-1234  [000] ....  1234.567893:     context_switch()

# 更实用：只追踪特定函数
echo do_page_fault > /sys/kernel/debug/tracing/set_ftrace_filter
echo function > /sys/kernel/debug/tracing/current_tracer
```

`ftrace` 还有一种特别有用的模式叫做**追踪点（tracepoints）**，它和动态函数追踪不同，是内核开发者在源码里**预先埋下的静态钩子**。全局追踪所有函数开销太大，但在关键路径上预设的追踪点提供了一个平衡点——只追踪最有意义的事件，开销控制在可接受范围内：

```c
// 内核源码里追踪点的定义方式（以调度器为例）
// kernel/sched/core.c
static void __sched notrace __schedule(unsigned int sched_mode)
{
    // ... 调度逻辑 ...

    // 这是一个追踪点：sched_switch
    // 正常情况下，这一行展开为几条 nop 指令，开销接近零
    // 当用户开启这个追踪点时，内核动态修补代码，让它执行真正的追踪逻辑
    trace_sched_switch(preempt, prev, next, prev_state);

    // ... 继续调度逻辑 ...
}
```

追踪点的命名遵循 `子系统名:事件名` 的格式，你可以用 `perf list` 看到所有可用的追踪点。常用的追踪点包括 `sched:sched_switch`（进程切换）、`syscalls:sys_enter_read`（进入read系统调用）、`kmem:kmalloc`（内存分配）、`block:block_rq_issue`（磁盘I/O请求发出）。

### 14.4 eBPF：可编程的内核观测框架

`perf` 和 `ftrace` 都是相对固定的工具——`perf` 采样，`ftrace` 追踪函数调用。但有时候你需要的是更复杂的分析："统计每个进程的系统调用延迟分布"、"找出哪些文件被打开次数最多"、"实时监控TCP连接建立失败的原因"。这些需求需要在内核里执行自定义的逻辑，而这正是 **eBPF（extended Berkeley Packet Filter）**的用武之地。

eBPF的基本思想是：允许用户向内核提交一段小程序，内核在特定的事件发生时执行这段程序。这段程序运行在内核空间，可以访问内核数据结构，但不能调用任意内核函数，不能循环太多次，不能造成内核崩溃——内核在加载eBPF程序之前，用一个**验证器（verifier）**对程序进行静态分析，拒绝任何可能导致问题的程序。

```c
// 一个简单的 eBPF 程序：统计每个进程的 read() 系统调用次数
// 用 C 语言写，被 clang 编译成 eBPF 字节码

// eBPF 程序使用"映射（map）"来和用户空间共享数据
// 这个 map 存储 PID -> 调用次数 的映射
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 1024);
    __type(key, u32);    // key 是 PID
    __type(value, u64);  // value 是计数
} read_count_map SEC(".maps");

// 这个程序挂载到 sys_enter_read 追踪点
// 每次任何进程调用 read() 系统调用时，这段代码被执行
SEC("tracepoint/syscalls/sys_enter_read")
int count_read(struct trace_event_raw_sys_enter *ctx)
{
    // 获取当前进程的 PID
    u32 pid = bpf_get_current_pid_tgid() >> 32;

    // 在 map 里查找这个 PID 的计数
    u64 *count = bpf_map_lookup_elem(&read_count_map, &pid);

    if (count) {
        // 已存在：计数加一
        __sync_fetch_and_add(count, 1);
    } else {
        // 首次出现：初始化为1
        u64 init = 1;
        bpf_map_update_elem(&read_count_map, &pid, &init, BPF_ANY);
    }

    return 0; // eBPF 程序必须返回0
}
```

用户空间的程序（用 Python 或 Go 写）负责加载这段 eBPF 程序、把它附加到追踪点，然后定期读取 map 里的数据并展示。整个过程里，最关键的数据统计在内核里高效完成，用户空间只是展示结果，开销极小。

eBPF 的应用场景非常广泛，已经远超出了最初的"包过滤"用途，渗透到了网络（Cilium用eBPF实现Kubernetes网络策略）、安全（Falco用eBPF检测异常系统调用）、性能分析（BCC工具集，包含几十个即用的eBPF分析工具）等领域。理解eBPF的运作方式，需要把前几节的很多知识综合起来：它通过追踪点（ftrace机制）挂钩，通过 map（哈希表，第七节）共享数据，通过 `bpf()` 系统调用（第十三节）加载程序，通过验证器保证安全。

### 14.5 用这些工具"看见"前几节讲的机制

学习工具最好的方式是用它们来验证你对原理的理解。这里我给你设计几个具体的实验，把工具和前几节的内容直接对应起来。

第一个实验是验证第四节的CFS调度。用 `perf sched record -a sleep 5` 记录5秒的调度事件，然后用 `perf sched latency` 查看每个进程的调度延迟分布。你会看到不同进程的"平均等待时间"——这就是 `vruntime` 机制在现实中的体现。优先级高（nice值低）的进程，等待时间明显更短。

第二个实验是验证第五节的缺页中断。用 `perf stat -e page-faults ./your_program` 统计你的程序触发了多少次缺页中断。对一个刚启动的程序多运行几次，你会发现第一次运行缺页数最多（冷启动，所有页都需要从磁盘加载），之后缺页数明显减少（文件系统和内存的缓存生效了）。这是第五节讲的懒分配和页缓存机制的直接体现。

第三个实验是验证第十节的锁竞争。`perf lock record -a sleep 5` 和 `perf lock report` 可以显示内核里各把锁的竞争情况，包括每把锁被争抢的次数、平均等待时间。在一个高并发的服务器上运行这个实验，你可能会看到某些锁（比如 `sched_rq` 的锁，或者内存分配的锁）有很高的竞争，这正是性能优化的着力点。

### 14.6 火焰图：性能分析的可视化利器

最后介绍一个和上述工具配合使用的可视化技术——**火焰图（Flame Graph）**，它是性能工程师Brendan Gregg发明的，现在已经成为性能分析领域最通用的可视化方式。

`perf record -g` 收集的是调用栈采样，但原始的文本输出很难快速定位问题。火焰图把这些采样数据转化成一张图：x轴表示采样的累积比例（宽度越宽说明占CPU时间越多），y轴表示调用栈深度（越高说明调用越深），每个格子代表一个函数，颜色只是为了区分。你看到一个宽而矮的"平台"，就意味着那个函数本身（不包括它的子调用）消耗了大量CPU时间，是优化的候选。

```bash
# 生成火焰图的完整命令序列
perf record -F 99 -g -a sleep 30  # 以99Hz采样，记录调用栈，持续30秒
perf script > out.perf             # 把采样数据转成文本

# 用 Brendan Gregg 的 FlameGraph 工具生成 SVG
stackcollapse-perf.pl out.perf > out.folded
flamegraph.pl out.folded > flame.svg

# 用浏览器打开 flame.svg，可交互地缩放和搜索
```

火焰图和内核原理的联系在于：它让你直观地"看见"各个子系统在实际负载下的相对开销。在一个数据库服务器的火焰图里，你可能看到30%的宽度被 `tcp_v4_rcv` 和相关函数占据（第九节的网络栈），20%被文件系统函数占据（第六节的VFS），15%被内存管理函数占据（第五节），还有大量细碎的调度器开销（第四节）。每一块"火焰"背后都是我们这个系列里讲过的原理，在真实负载下按比例呈现出来。

### 本节小结

这一节我们认识了三套性能分析工具。`perf` 通过硬件性能计数器以极低的开销进行采样，回答"CPU时间花在哪里"；`ftrace` 通过动态代码修补和预设追踪点，精确记录内核函数的执行轨迹；`eBPF` 允许在内核里运行自定义的分析逻辑，在安全性和灵活性之间取得平衡。火焰图则把这些工具收集的数据变成直观可读的可视化。

这三套工具之所以能工作，正是因为它们深度利用了内核各个子系统预先设计好的"观测钩子"——追踪点、动态修补点、`perf_event` 框架。内核的设计者在构建这些子系统时，就把"可观测性"当作一等公民来考虑。这种"在设计时就考虑如何被观测"的思想，是构建复杂系统的重要工程哲学，值得你在自己的系统设计中借鉴。
