## 第三节：所有权（Ownership）

---

### 先建立直觉：内存的"责任人"问题

在 C 里，当你 `malloc` 一块内存，编译器不知道、也不关心谁负责 `free` 它。这个责任完全落在程序员身上。如果你忘了 `free`，就内存泄漏；如果你 `free` 了两次，就 double free；如果你 `free` 之后还在用那个指针，就是 use-after-free。这三类问题加在一起，占了现实世界中大量安全漏洞的根源。

Rust 的核心洞见是：**每一块内存，在任意时刻，都应该有且仅有一个明确的"责任人"**。当这个责任人消失，内存就自动释放。这个"责任人"的概念，就是 Rust 里的**所有者（owner）**。

---

### 所有权的三条规则

整个所有权系统建立在三条简单的规则上，所有复杂的行为都从这里派生出来：

**规则一：Rust 中的每一个值都有一个所有者（owner）。** 规则二：**在任意时刻，一个值只能有一个所有者。** 规则三：**当所有者离开作用域（scope），这个值就会被自动丢弃（drop）。**

就这三条。让我们一条一条地把它们变得具体。

---

### 规则三：作用域与自动释放

先看最直观的规则三。你在 C 里已经知道"局部变量在函数返回时自动消失"，Rust 的做法和这个完全一致——只不过对堆内存也一样适用：

```rust
fn main() {
    // s 在这里还不存在

    {
        let s = String::from("hello"); // s 从这里开始有效
                                       // String 是堆分配的字符串，相当于 C 的 malloc + 字符数据

        // 用 s 做一些事情
        println!("{}", s);

    } // ← 这个花括号结束时，s 的作用域结束
      //   Rust 自动在这里调用 drop(s)，释放堆内存
      //   不需要你写 free(s)！

    // s 在这里已经无效，访问它会编译错误
}
```

注意这里用的是 `String`，不是 `&str`。在 Rust 里这两个东西有明确区别：`&str` 是对某段字符串数据的**引用**（通常指向程序的静态区），而 `String` 是一个**堆分配的、可增长的**字符串，类似 C++ 的 `std::string` 或 C 里手动 `malloc` 的字符数组。我们选 `String` 来演示，正是因为它涉及堆内存，能让所有权的效果更清晰。

这个自动释放的机制叫做 **RAII**（Resource Acquisition Is Initialization），C++ 也有这个概念。当变量离开作用域时，Rust 会调用一个特殊的 `drop` 函数来做清理工作。你不需要手动调用它——事实上 Rust 不允许你在错误的时机调用它。

---

### 规则二：移动（Move）

"一个值只能有一个所有者"是最容易让 C 程序员感到意外的规则。来看一个例子：

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // 你以为这是"复制"，但实际上是"移动"

    println!("{}", s1); // 编译错误！s1 已经不再有效
}
```

为什么？想一想如果 `s2 = s1` 是简单的"复制"，会发生什么。`String` 在内存里长这个样子：

```
栈上的 s1:          堆上:
┌──────────────┐    ┌─────────────────┐
│ ptr ─────────┼───►│ h e l l o       │
│ len: 5       │    └─────────────────┘
│ capacity: 5  │
└──────────────┘
```

`String` 在栈上只存了三个字段：一个指向堆数据的指针、长度、和容量。如果 `s2 = s1` 只是把这三个字段复制一份，那 `s1` 和 `s2` 就都指向同一块堆内存。当 `s1` 离开作用域，`drop` 释放那块堆内存；`s2` 离开作用域，`drop` 再次释放——这就是 double free，正是 Rust 要消灭的 bug。

所以 Rust 的处理方式是：`let s2 = s1` 之后，**所有权从 `s1` 转移（move）给 `s2`**。`s1` 立刻作废，编译器不再允许你使用它。内存里只有一份堆数据，只有一个所有者（`s2`），所以只会被释放一次。

这个"转移所有权"的操作，Rust 叫做 **move**。可以把它理解成：堆内存的"证书"只有一张，`let s2 = s1` 就是把这张证书从 `s1` 转给了 `s2`，`s1` 手里什么也没有了。

---

### 函数调用也会发生 Move

这是很多初学者第一次遇到"编译不过"时真正困惑的地方。Move 不只发生在变量赋值时，**把值传给函数也会发生 Move**：

```rust
fn takes_ownership(s: String) { // s 的所有权转移进了这个函数
    println!("{}", s);
} // s 在这里离开作用域，堆内存被释放

fn main() {
    let s = String::from("hello");

    takes_ownership(s); // s 的所有权移动进了函数

    println!("{}", s); // 编译错误！s 已经被移走了
}
```

这个行为对 C 程序员来说非常反直觉，因为 C 里函数参数是按值传递——你传的是一个副本，原来的变量不受影响。但 C 里的"副本"对于指针来说只是复制了指针本身，并没有复制堆上的数据，这正是问题所在。Rust 选择了一个更诚实的语义：如果传递之后原来的变量还能继续用，那就必须明确地"克隆"数据；否则就是移动，原来的变量作废。

---

### Clone：当你真的需要复制

如果你确实需要两份独立的堆数据，可以显式调用 `.clone()`：

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1.clone(); // 深拷贝：堆上的数据也复制了一份

    // 现在 s1 和 s2 各自拥有独立的堆内存
    println!("s1 = {}, s2 = {}", s1, s2); // 完全正常！
}
```

`.clone()` 对应的是 C 里的"深拷贝"。Rust 让你显式调用它，是因为深拷贝往往有性能开销，Rust 不希望这件事在你不知情的情况下悄悄发生。每一处 `.clone()` 都是一个明确的信号：_这里我选择付出复制的代价_。

---

### Copy：栈上的数据是例外

你可能已经注意到一个问题：那整数、浮点数这些基础类型怎么办？难道 `let y = x` 之后 `x` 也作废了？来试一下：

```rust
fn main() {
    let x = 5;
    let y = x; // 对于整数，这是 Copy，不是 Move

    println!("x = {}, y = {}", x, y); // 完全正常！x 没有作废
}
```

对于完全存储在栈上、大小已知且固定的类型（比如所有整数类型、浮点类型、布尔、字符，以及只包含上述类型的元组），Rust 实现了一个叫做 **`Copy` 的 trait**。拥有 `Copy` 的类型在赋值或传参时会自动做**浅拷贝**，不会发生 Move，原来的变量仍然有效。

为什么浅拷贝对它们是安全的？因为它们根本没有堆内存，全部数据就在栈上，复制一份完全没有任何问题，也不存在"谁来 free"的问题。

你可以用这个简单的判断标准：**如果一个类型"丢掉"了没有任何清理工作要做，它就是 `Copy` 的**。`String` 不是 `Copy` 的，因为丢掉它之前必须释放堆内存；而 `i32` 是 `Copy` 的，因为丢掉它什么都不用做。

---

### 回到第一节的问题

还记得第一节末尾那段 C 代码吗？

```c
int* get_value() {
    int x = 42;
    return &x; // 返回局部变量的地址：x 在函数返回时消失，这个指针成了悬空指针
}
```

在 Rust 里写等价的代码：

```rust
fn get_value() -> &i32 {
    let x = 42;
    &x // 试图返回 x 的引用
} // x 在这里 drop，&x 成了悬空引用
```

Rust 编译器会直接报错，告诉你"x 活得不够长"（`x does not live long enough`）。这个检查就是由所有权系统的规则推导出来的——编译器知道 `x` 的生命周期在函数结束时终止，而你想把一个指向它的引用传出去，这在逻辑上是矛盾的。这个矛盾在 C 里只会在运行时才暴露（如果你运气不好，甚至不会立刻崩溃），而在 Rust 里编译阶段就被拒绝了。

---

### 本节小结

所有权系统的核心是：**每块内存有唯一的主人，主人消失则内存自动释放，所有权转移之后原持有者作废**。这三条规则像一套逻辑自洽的公理，从它们出发可以推导出 Rust 内存安全的所有保证。

但你现在可能有一个很自然的疑问：如果每次传参都会把值移走，我要用一个值很多次岂不是非常麻烦？难道每次都要 `.clone()` 一份吗？

这个问题问得非常好，也正是下一节要解决的——**第四节：借用与引用（Borrowing & References）**。Rust 的答案是：你不必转移所有权，你可以"借"出去用一用，用完还回来。这套借用机制，才是你日常写 Rust 代码时最频繁打交道的工具。

## 第四节：借用与引用（Borrowing & References）

---

### 上节留下的问题

上一节结尾我们发现了一个实际编程中的痛点：如果每次把值传给函数都会发生 Move，那这个值就"进去出不来"了。比如你想写一个函数来计算字符串的长度，你总不能每次调用完之后那个字符串就不能用了吧？

一个笨办法是：函数把值"还回来"——

```rust
fn calculate_length(s: String) -> (String, usize) {
    let len = s.len();
    (s, len) // 把所有权和计算结果一起返回
}

fn main() {
    let s = String::from("hello");
    let (s, len) = calculate_length(s); // 把 s 还回来
    println!("'{}' 的长度是 {}", s, len);
}
```

这段代码可以编译，但非常别扭。每个函数都要把参数"还回来"，代码会变得非常啰嗦。这显然不是正确的打开方式。

Rust 的真正答案是：**引用（reference）**。

---

### 引用：借出去，用完还回来

引用的概念非常直观：你可以把一个值的**引用**传给函数，函数通过引用来访问这个值，但**不拥有它的所有权**。函数结束时，引用消失，但原来的值还在原来的主人手里。这个行为就叫做**借用（borrowing）**。

语法上，创建引用用 `&`，访问引用指向的值用 `*`（解引用）——这和 C 的指针语法一模一样：

```rust
fn calculate_length(s: &String) -> usize {
    // s 是对 String 的引用，不是 String 本身
    // 函数结束时 s 消失，但它指向的 String 不会被 drop
    s.len()
}

fn main() {
    let s = String::from("hello");

    // & 创建一个指向 s 的引用，传给函数
    // s 本身的所有权没有转移
    let len = calculate_length(&s);

    // s 在这里仍然有效！
    println!("'{}' 的长度是 {}", s, len);
}
```

内存里的样子是这样的：

```
栈上的 s:             堆上:
┌──────────────┐      ┌───────────────┐
│ ptr ─────────┼─────►│ h e l l o     │
│ len: 5       │      └───────────────┘
│ capacity: 5  │             ▲
└──────────────┘             │
                             │
栈上的 &s（引用）:            │
┌──────────────┐             │
│ ptr ─────────┼─────────────┘
└──────────────┘
```

引用是一个指向 `s` 的指针，而 `s` 本身又有一个指向堆数据的指针。从这个角度看，Rust 的引用和 C 的指针在底层是同一回事。关键差别在于：Rust 的引用由编译器保证**永远有效**——你不可能拿到一个悬空引用。

---

### 不可变引用的限制：只能读，不能写

默认的引用 `&T` 是**不可变引用**，通过它只能读取数据，不能修改：

```rust
fn try_to_modify(s: &String) {
    s.push_str(", world"); // 编译错误！不能通过不可变引用修改值
}
```

这个限制很有道理：你只是"借"来看看，没有权利改动别人的东西。如果你确实需要通过引用来修改值，要用**可变引用** `&mut T`。

---

### 可变引用：`&mut`

```rust
fn add_world(s: &mut String) {
    s.push_str(", world"); // OK，通过可变引用可以修改
}

fn main() {
    let mut s = String::from("hello"); // 注意：原变量本身也必须是 mut
    add_world(&mut s);                 // 传递可变引用
    println!("{}", s);                 // 输出 "hello, world"
}
```

这里有两个 `mut` 需要同时存在，原因是逻辑上的：如果原变量本身是不可变的（`let s`），那无论如何都不应该允许通过引用来改变它，所以可变引用要求原变量本身也必须是 `mut` 的。

---

### 借用的核心规则

现在来到这一节最重要的地方。Rust 对引用的使用有一套严格的规则，这套规则是编译器防止数据竞争的核心机制。规则很简单，但蕴含着深刻的设计意图：

**在同一个作用域内，对于同一个值，要么只能有一个可变引用，要么可以有任意多个不可变引用，但两者不能同时存在。**

用更口语化的方式说：**你要么允许多个人同时读，要么允许一个人独占写，但不能又读又写**。

来看编译器如何执行这条规则：

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;     // OK，第一个不可变引用
    let r2 = &s;     // OK，第二个不可变引用，多个只读是允许的
    let r3 = &mut s; // 编译错误！已经有不可变引用存在，不能再创建可变引用

    println!("{}, {}, {}", r1, r2, r3);
}
```

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &mut s; // OK，第一个可变引用
    let r2 = &mut s; // 编译错误！同一时刻只能有一个可变引用

    println!("{}, {}", r1, r2);
}
```

---

### 为什么是这条规则？

这条规则并不是 Rust 凭空发明的限制，它对应的是并发编程中一个根本性的问题：**数据竞争（data race）**。

数据竞争发生的条件正好是这三个同时成立：两个及以上的指针同时指向同一块数据，至少一个指针在做写操作，并且没有同步机制。Rust 的引用规则精确地杜绝了前两个条件——要么多个只读指针共存（没有写，安全），要么唯一一个可写指针存在（没有其他人在读，安全）。两者不能同时存在。

这意味着，**Rust 在单线程代码里的引用规则，和它在多线程代码里的安全保证是同一套系统的两个侧面**。你写 Rust 的习惯，天然就是线程安全的写法。

---

### 引用的作用域：比你想象的更智能

初学者经常遇到一个困惑：引用的作用域到底在哪里结束？Rust 的现代版本（引入了"Non-Lexical Lifetimes"）对此有一个直觉友好的处理方式——引用的作用域**在它最后一次被使用的地方结束**，而不是在语法上的花括号结束处。这意味着下面的代码是合法的：

```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;
    let r2 = &s;
    println!("{} and {}", r1, r2);
    // r1 和 r2 在这里之后再没被用过，它们的作用域在这里结束

    // 所以下面创建可变引用是合法的！
    let r3 = &mut s;
    println!("{}", r3);
}
```

编译器足够聪明，能看出 `r1`、`r2` 在创建 `r3` 之前就已经"用完了"，因此不存在冲突。这个特性让借用规则在实践中比初学时想象的要宽松一些。

---

### 悬空引用：Rust 彻底杜绝的 bug

回到第一节和第三节都提到的悬空指针问题。在 C 里这很容易犯错，但在 Rust 里，如果你试图返回一个指向局部变量的引用，编译器会直接拒绝：

```rust
fn dangle() -> &String {   // 试图返回一个引用
    let s = String::from("hello"); // s 是一个局部变量
    &s                             // 返回 s 的引用
}  // s 在这里被 drop，&s 成了悬空引用——编译器在这里报错！
```

编译器会告诉你：`s` 活得不够长（`s does not live long enough`）。它追踪了引用的生命周期，发现引用会"活"得比它指向的数据更长，这在逻辑上是矛盾的，直接拒绝编译。

正确的做法是返回 `String` 本身，把所有权移出去：

```rust
fn no_dangle() -> String {
    let s = String::from("hello");
    s // 移动所有权，而不是返回引用
}
```

---

### 一个思考练习

在继续之前，试着在脑子里判断下面这段代码能否编译，为什么：

```rust
fn main() {
    let mut v = String::from("hello");

    let r = &v;              // ①
    v.push_str(" world");    // ②
    println!("{}", r);       // ③
}
```

答案是：**编译失败**。`②` 处 `push_str` 需要对 `v` 进行可变访问，但 `①` 创建的不可变引用 `r` 在 `③` 处还被用到，它的作用域覆盖了 `②`。换句话说，在 `r` 还"活着"的时候，你试图修改它所引用的数据，这违反了"不可变引用存在期间不能有可变访问"的规则。

如果把 `println!` 移到 `push_str` 之前，代码就合法了——因为 `r` 的作用域在 `println!` 之后就结束了，不再覆盖 `push_str` 的调用。这个练习很好地展示了"引用的作用域到最后一次使用为止"这条规则在实践中的意义。

---

### 本节小结

引用和借用是你日常写 Rust 时最频繁用到的工具。它们让你在不转移所有权的前提下访问数据，同时编译器通过"要么多个只读，要么唯一可写"这一条规则，从根本上消灭了悬空引用和数据竞争。

到目前为止，我们一直在讨论所有权和引用的规则，但还没有深入讨论编译器是**如何追踪**引用是否合法的。这背后有一个更系统化的机制，叫做**生命周期（Lifetime）**。不过生命周期稍微抽象一些，我们暂时先把它放一放，先在下一节学一个更接地气的话题：**第五节：结构体（Struct）**。有了结构体，我们才能开始组织真实的数据，也能更自然地引出后续的生命周期讨论。
