## 第三讲：存储系统——CPU 与内存之间那道鸿沟

我说过这是我个人最喜欢的一讲。原因有两个：第一，它解释了你写过的几乎每一段代码的性能秘密——为什么有些"看起来一样"的代码能差出十倍；第二，它体现了计算机科学里一个极深刻的思想——**用层次化的近似来突破物理极限**。学完这一讲，你看代码的眼神会变。

这一讲很长，因为存储系统是整门课实战价值最大的部分。我会按这样的顺序展开：先讲存储墙这个根本矛盾（我们要解决什么），再讲局部性原理（解决问题的关键观察），然后是存储层次结构（架构层面的方案），接着是缓存的具体设计（这是核心，会讲得很细），然后是虚拟内存（让程序看到"无限内存"的魔法），最后是一些你能在 C++ 里亲手验证的实验。

### 一、存储墙：CPU 和内存之间的鸿沟

我们从一个具体的数字开始，因为这个数字决定了现代计算机设计的几乎一切。

一颗主流的现代 CPU，时钟频率大约 3-5 GHz。这意味着它每秒能执行数十亿次指令——具体到一条简单的算术指令，大约**0.3 纳秒**就能完成。

而主内存（DRAM）的访问延迟是多少？大约 **100 纳秒**。

请你慢慢消化这个数字。CPU 完成一次加法的时间，和它从内存取一个数据的时间，相差**约 300 倍**。换个比喻：如果 CPU 执行一条指令是"眨一下眼"（0.3 秒），那么访问一次内存就是**站在原地等 5 分钟**。

这个差距并不是天生这么大的。1980 年代早期，CPU 时钟频率只有几 MHz，内存延迟也大致匹配，两者步调一致。但是从那时起，**CPU 的速度几乎每两年翻一番（摩尔定律的体现），而 DRAM 的速度增长极其缓慢**——主要因为 DRAM 受限于电容充放电的物理过程，而 CPU 速度受限于晶体管的开关速度，两者改进规律不同。几十年累积下来，CPU 和内存之间形成了一道巨大的鸿沟。这道鸿沟有一个广为人知的名字：**存储墙（Memory Wall）**。

存储墙意味着什么？意味着如果一颗 5 GHz 的 CPU 每条指令都要从内存取数据，它实际上只能以**几十 MHz 的速度工作**——快出来的部分全在等内存。这相当于把一台跑车扔到泥泞路上，引擎再强也跑不快。

那有没有办法造出又快又大的内存呢？理论上可以，但**经济上不可行**。让我把这背后的原理摊开。

存储器有两大类：**SRAM（静态随机存取存储器）** 和 **DRAM（动态随机存取存储器）**。SRAM 用 6 个晶体管存 1 位（一个由两个反相器构成的"双稳态"电路加上两个访问晶体管），它快（亚纳秒级）、不需要刷新、读写对称。但每位用 6 个晶体管意味着同样面积存的数据少，所以**贵**。DRAM 用 1 个晶体管加 1 个电容存 1 位（电容充电代表 1，放电代表 0），密度高、便宜，但慢（电容充放电需要时间），而且电容会漏电，必须**定期刷新**（每隔几毫秒重写一次所有数据，这就是 DRAM 中 D="Dynamic" 的来历）。

如果你想造一台 16GB 全 SRAM 的电脑，理论上很快，但成本会让你买不起——SRAM 的每位成本大约是 DRAM 的 100 倍。反过来，全 DRAM 的电脑会因为存储墙而慢得无法忍受。

工程上的解决方案不是"二选一"，而是"全都要"——这就是接下来要讲的存储层次结构。但在那之前，我们必须先理解一个让"全都要"成为可能的关键观察。

### 二、局部性原理：一切的基石

如果程序访问内存是完全随机的——这次访问 0x1000，下次访问 0xDEADBEEF，再下次访问 0x42——那么任何"加速"都是徒劳的，CPU 永远只能以最慢那级存储的速度工作。

幸运的是，**真实程序的内存访问根本不是随机的，而是高度规律的**。这个观察被称为**局部性原理（Locality Principle）**，是整个存储系统设计的灵魂。它有两种形式：

**时间局部性（Temporal Locality）**：**最近访问过的数据，很可能在不久后再次被访问**。

举几个你熟悉的例子。一个 `for` 循环里的循环变量 `i`，在整个循环期间被反复读写——这是时间局部性。一个被频繁调用的函数（比如递归函数自己），它的指令在短时间内被反复执行——这也是时间局部性。一个全局配置变量，在程序运行中被多处引用——还是时间局部性。

**空间局部性（Spatial Locality）**：**访问过某个地址的数据，很可能不久后会访问它附近的地址**。

例子同样无处不在。遍历数组 `for (i=0; i<n; i++) sum += a[i]`——你访问 `a[0]`、`a[1]`、`a[2]`……每个紧挨着上一个，这是空间局部性的最纯粹形式。读一个结构体的多个字段——它们在内存里相邻。顺序执行的指令——下一条指令在当前指令的下一个地址。

这两个原理为什么成立？根本原因是**程序是人类写出来的，人类的算法和数据组织方式天然带有结构**。我们用循环处理批量数据（产生空间局部性），我们用变量记住中间状态（产生时间局部性），我们用函数封装重复逻辑（两种局部性兼有）。如果有一种"反局部性"的程序——它故意每次访问都跳到完全不相关的地址——它的性能会差到难以忍受，但人也几乎写不出这样的程序，因为这种逻辑没有意义。

**局部性原理是一个经验观察，不是数学定理**。但它在实践中如此普遍、如此可靠，以至于整个现代计算机系统都建立在它之上。下面要讲的存储层次和缓存，本质都是在**利用局部性原理把"平均访问时间"拉到接近最快那级的速度**。

### 三、存储层次结构：用一层近似突破物理极限

既然程序访问有局部性，工程师就有了一个绝妙的想法：**把"最近访问过的、可能再次访问的"少量数据放到一个又快又小的存储器里，把"不常用的"大量数据放到慢但大的存储器里**。这就是**存储层次结构（Memory Hierarchy）**。

现代计算机的存储层次大致是这样的（数字会因具体硬件不同而变化，我给的是一个典型的数量级）：

```
层级               容量           访问延迟          每位成本
─────────────────────────────────────────────────────
寄存器             几百字节        < 0.3 ns         极高
L1 缓存            ~32 KB         ~1 ns            很高
L2 缓存            ~256 KB        ~3 ns            高
L3 缓存            ~8-32 MB       ~10 ns           中
主存（DRAM）        ~16-64 GB      ~100 ns          低
SSD                ~1 TB          ~50,000 ns       很低
HDD                ~10 TB         ~5,000,000 ns    极低
```

请仔细看这张表，它有几个值得注意的特征：

**第一，每下一层，容量大约扩大 10-100 倍，速度慢 10-100 倍，成本降低同样的比例**。这是一个金字塔结构，越往下越大、越慢、越便宜。

**第二，从寄存器到 HDD，速度差距是七八个数量级**。HDD 比寄存器慢一千万倍。如果寄存器访问是"眨眼"（0.3 秒），那访问 HDD 就是"站在原地等两个月"。

**第三，每一层都对它上一层是"备份"，对它下一层是"缓存"**。CPU 直接访问的是寄存器；寄存器找不到的去 L1 找；L1 没有的去 L2 找；以此类推。每一层都希望"我自己就够用"，把对下一层的访问降到最低。

这个结构的精妙之处在于：**只要每一层的命中率足够高，平均访问时间就接近最快那一层的速度**。

让我用一个简单的算式说明。假设 L1 缓存的命中率是 95%（意思是 CPU 想访问的数据 95% 的情况下能在 L1 里找到），L1 的延迟是 1 ns，未命中（剩下 5%）需要去主存找，延迟 100 ns。那么平均访问时间是：

Tavg=0.95times1+0.05times100=0.95+5=5.95textns

平均访问时间约 6 ns——比 100 ns 的纯主存访问快了 17 倍。**这就是局部性原理 + 层次结构的力量**。

如果命中率提高到 99%：

Tavg=0.99times1+0.01times100=0.99+1=1.99textns

接近 L1 自己的速度了！这给你一个非常重要的直觉：**缓存命中率从 95% 到 99% 的"小"提升，能让性能从 6 ns 跳到 2 ns，提升 3 倍**。这就是为什么编译器、操作系统、库设计者都在拼命优化缓存命中率——每一个百分点都是真金白银的性能。

### 四、缓存的工作原理：从一个简单问题开始

存储层次的思想已经清楚了，但魔鬼藏在细节里。CPU 想访问内存地址 `0x1000`，缓存怎么知道自己里面有没有这个地址的数据？如果有，怎么找到？如果没有，怎么从主存把它装进来？装进来时如果缓存满了，赶谁出去？

这些问题的答案就是**缓存的具体设计**，也是这一讲最技术性的部分。我会从一个简单的问题出发，让设计自然涌现出来。

**问题**：缓存有 32 KB，主存有 16 GB。我手上有一个 64 位的内存地址，怎么判断这个地址对应的数据是否在缓存里？

最朴素的想法是把缓存做成一个"地址→数据"的字典：每次查询遍历整个缓存，对比地址。但这显然太慢——遍历需要时间，违背了"缓存要快"的初衷。

第二个想法：**用地址的某些位作为索引，直接定位到缓存的某个位置**。这是哈希表的思路。下面我们逐步细化这个思路。

#### 4.1 缓存行：以"块"为单位组织

第一个关键设计决策：**缓存不是按字节存储的，而是按"块"存储的**。每个块（在缓存里也叫**缓存行，cache line**）通常是 64 字节。也就是说，当 CPU 想访问内存地址 `0x1000` 处的 4 字节整数时，缓存会把包含这个地址的整个 64 字节块（比如 `0x1000` 到 `0x103F`）都装进来。

为什么以块为单位？这是空间局部性的直接利用。

64 字节这个数字也不是随便选的——它是在"块太大浪费"和"块太小利用率低"之间的工程权衡。块越大，单次能利用的空间局部性越多；但太大会导致很多带进来的数据用不上（"污染"缓存），还会延长一次装载的时间。64 字节是几十年实践收敛出来的甜点。

由此推出一个**重要事实**：**内存地址被自然地划分为"块号"和"块内偏移"两部分**。对于 64 字节的块，地址的低 6 位是块内偏移（因为 26=64），剩下的高位是块号。

```
64 位地址：[ ............块号............ | 块内偏移 (6 位) ]
```

CPU 访问任何地址，先取出高位算出块号，再取出低 6 位定位到块内的某个字节。

#### 4.2 三种映射方式：缓存的核心设计

现在进入缓存设计最核心的问题：**主存的某个块，应该放到缓存的哪个位置？**

历史上有三种方案，分别是直接映射、全相联映射、组相联映射。它们代表了不同的"灵活性 vs 复杂度"权衡。

##### 直接映射（Direct-Mapped）

**最简单的方案**：每个主存块只能放到缓存里的**一个特定位置**。规则是 `缓存位置 = 主存块号 mod 缓存块数`。

举例：缓存有 512 个块（32 KB / 64 字节），主存块号 0、512、1024、1536……都被映射到缓存的位置 0；主存块号 1、513、1025……都被映射到缓存的位置 1。

地址被划分成三部分：

```
[ 标记 (Tag) | 索引 (Index) | 块内偏移 (Offset) ]
```

**索引**直接告诉你"去缓存的哪个位置查"——对于 512 个缓存块，索引是 9 位（29=512）。**标记**用来区分"恰好被映射到同一位置的不同主存块"——因为缓存位置 0 可能存的是主存块 0，也可能是主存块 512、1024……所以缓存还要存一个标记说明"我现在装的到底是哪个块"。

查询过程：

1. 拆出地址的索引部分，去缓存对应位置取出标记和数据。
2. 比较取出的标记与地址的标记部分。
3. 相等：缓存命中（hit），用偏移取出数据。
4. 不等：缓存未命中（miss），需要从主存装载该块到这个位置（替换掉原来的内容）。

直接映射的**优点**：硬件极简单——一个比较器就能判断命中。**缺点**：极不灵活。如果你的程序碰巧反复访问块号 0 和块号 512（它们映射到同一位置），那么这两个块会不断把对方踢出缓存，造成**抖动（thrashing）**——即使缓存还有大量空闲空间，这两个块也会反复 miss。

##### 全相联映射（Fully Associative）

**最灵活的方案**：每个主存块可以放到缓存的**任意位置**。

地址只分两部分：

```
[ 标记 (Tag) | 块内偏移 (Offset) ]
```

没有索引，因为不知道该去哪个位置查。查询时**必须并行比较缓存中所有块的标记**——硬件上需要给每个缓存块配一个比较器，全部并行工作。

全相联的**优点**：没有冲突，只要缓存还有空位，新块永远能装进去。**缺点**：硬件极昂贵——一个 512 块的缓存需要 512 个并行比较器，这在大缓存中是不可接受的。所以全相联只用于很小的缓存（比如 TLB，我们等下会讲）。

##### 组相联映射（Set-Associative）

**折中方案，也是现代 CPU 的实际选择**：把缓存分成若干"组"，每个主存块通过取模映射到一个特定的"组"，但**在组内可以放到任意位置**。

如果每组有 k 个位置，就叫 **k 路组相联**。比如 4 路组相联意味着每个组有 4 个槽位，主存块映射到组之后可以选这 4 个槽位中的任何一个。

地址划分：

```
[ 标记 (Tag) | 组索引 (Set Index) | 块内偏移 (Offset) ]
```

查询：用组索引找到组，组内并行比较 k 个标记（只需要 k 个比较器）。

组相联是直接映射（k=1，每组一个块）和全相联（k=缓存块数，只有一个组）的统一框架——它们是两个极端，组相联是中间的连续谱。

**真实数字**：现代 CPU 的 L1 缓存通常是 8 路组相联，L2 是 8-16 路，L3 是 16-32 路。这是几十年优化出来的工程结果——既保留了一定的灵活性（远低于直接映射的冲突率），又避免了全相联的硬件成本。

#### 4.3 替换策略：缓存满了怎么办

当一个新块要进入缓存的某个组，但组已经满了，必须挑一个旧块踢出去。怎么挑？这就是**替换策略**。

最理想的策略叫 **Belady 最优算法**：踢掉"未来最久不会用的"那个块。但这需要预知未来——程序当然没法预知。Belady 算法只是一个理论上限，用来评估其他策略的好坏。

实际使用的策略：

**LRU（Least Recently Used，最近最少使用）**：踢掉"最久没被访问过的"块。它是对 Belady 的近似——基于时间局部性，最久没被访问的块未来也最不可能被访问。LRU 的命中率通常很好，但**精确的 LRU 实现需要给每个块维护一个"最近使用时间戳"，硬件代价不低**。所以 8 路以上的组相联缓存通常用 LRU 的近似版本（比如伪 LRU、Tree-PLRU），用一两个状态位近似地跟踪访问顺序。

**FIFO（先进先出）**：踢掉最早装入的块。简单但效果一般，没有充分利用时间局部性。

**Random（随机）**：随机挑一个踢掉。听起来很糙，但实测效果惊人地不差——而且硬件超级简单。某些 ARM 处理器就用 Random 替换。

**LFU（Least Frequently Used，最少使用频率）**：踢掉"被访问次数最少的"。直觉上不错，但有"老数据吃掉新数据"的问题——一个早期被频繁访问后来没人用的块，可能因为历史计数高而赖着不走。

#### 4.4 写策略：写操作的复杂性

读操作的逻辑相对简单：缓存有就用缓存，没有就从主存装载。**写操作复杂得多**，因为修改数据后，缓存和主存的内容可能不一致——必须决定何时把修改同步到主存。

两种主要策略：

**写直达（Write-Through）**：每次写操作同时更新缓存和主存。优点是缓存和主存始终一致，简单。缺点是每次写都要等慢的主存——除非配合**写缓冲区（write buffer）**：把写请求先放入一个 FIFO 队列，CPU 立即继续执行，让队列异步地把数据写到主存。

**写回（Write-Back）**：写操作只更新缓存，给该块打一个**脏位（dirty bit）**标记。只有当这个块被替换出去时，才把脏的数据写回主存。优点是绝大多数写操作不用接触主存，性能高。缺点是缓存和主存可能长时间不一致——这在多核 CPU 中会引发**缓存一致性**问题（多个核心都缓存了同一块内存，谁的版本是对的？），需要专门的协议（如 MESI 协议）来管理。

现代 CPU 的 L1、L2、L3 几乎都是写回策略。MESI 协议是个复杂主题，408 大纲里只是简单提及，我们这里也只点到为止——核心思想是给每个缓存行加四个状态（Modified、Exclusive、Shared、Invalid），通过总线广播让多个核心的缓存协调。如果你将来做并发编程，特别是无锁数据结构，会遇到一个叫"伪共享（false sharing）"的性能问题，根源就在 MESI 协议——这是我之后可能专门展开的话题。

#### 4.5 缓存未命中的三种类型

最后一个理论小点。当缓存未命中时，原因可以分为三类，这个分类很有名，叫 **3C 模型**：

**Compulsory miss（强制未命中）**：第一次访问某块数据，缓存里当然没有。这是无法避免的——除非用预取（prefetch）技术提前把数据装进来。

**Capacity miss（容量未命中）**：程序的工作集（working set，活跃使用的数据总量）超过了缓存容量，导致旧数据被踢出后又重新需要。这只能靠扩大缓存或减小工作集（优化数据结构）来缓解。

**Conflict miss（冲突未命中）**：程序的工作集小于缓存容量，但因为映射冲突（多个块映射到同一组）导致的未命中。提高组相联度可以减少这类未命中。

理解 3C 模型的实战意义：当你发现程序缓存未命中率高时，要分析是哪一类。如果是 capacity miss，要考虑缩小数据规模或分块处理（cache blocking）；如果是 conflict miss，可能是数据布局让多个常用结构落到同一缓存组——可以通过对齐、填充等手段错开。

### 五、虚拟内存：让程序看到"无限内存"

讲完缓存，我们再上一层抽象。前面讨论的都是"物理内存"——CPU 访问的内存地址直接对应主存中的物理位置。但**现代操作系统不是这样工作的**。

考虑这些问题：你的电脑同时运行十几个进程（浏览器、IDE、Q……），它们各自都以为自己拥有完整的内存吗？如果浏览器写到地址 `0x1000`，IDE 也写到 `0x1000`，它们会互相覆盖吗？如果你的程序需要 8 GB 内存，但电脑只有 4 GB 物理内存，能运行吗？

这些问题的答案都涉及一个伟大的发明：**虚拟内存（Virtual Memory）**。

#### 5.1 核心思想

虚拟内存的核心思想是：**让每个进程都看到一个独立的、连续的、巨大的"虚拟地址空间"**（64 位系统下理论上 264 字节，实际通常 48 位，约 256 TB）。这个空间里的地址叫**虚拟地址**。当 CPU 实际访问内存时，硬件会把虚拟地址翻译成**物理地址**，再去物理内存读写。

这个翻译过程对程序完全透明——程序写 `*p = 42` 时不知道也不关心 `p` 的虚拟地址会被映射到物理内存的什么位置。这种"接口与实现分离"的思想，又一次出现了。

虚拟内存解决了三大问题：

**进程隔离**：每个进程有独立的虚拟地址空间，进程 A 的 `0x1000` 和进程 B 的 `0x1000` 被映射到不同的物理位置，互不干扰。这是现代操作系统稳定性和安全性的基石。

**内存的逻辑扩展**：如果物理内存不够，可以把暂时不用的内存"换出"到硬盘上的**交换区（swap）**，需要时再"换入"。这样程序看到的虚拟内存可以远大于物理内存。代价是访问被换出的页时极慢（要从硬盘读），这个事件叫**缺页中断（page fault）**。

**灵活的内存管理**：可以让多个进程共享同一段物理内存（比如多个进程都加载了同一个动态库 `libc.so`，物理内存里只需要一份）；可以给每个内存区域设权限（代码段只读不可写，数据段可读写不可执行——这是防止某些攻击的关键）；可以延迟分配（请求 1GB 时不真的分配，等真的访问时再给）。

#### 5.2 分页：虚拟内存的实现机制

虚拟内存怎么实现？最主流的机制叫**分页（paging）**：把虚拟地址空间和物理地址空间都切成固定大小的"页"（page），通常每页 4 KB。地址翻译以页为单位进行。

虚拟地址被划分为：

```
[ 虚拟页号 (VPN) | 页内偏移 (Offset, 12 位) ]
```

物理地址同理：

```
[ 物理页号 (PPN) | 页内偏移 (Offset, 12 位) ]
```

注意页内偏移**两者相同**——翻译只改变页号，不改变页内位置。4 KB 页对应 12 位偏移（212=4096）。

操作系统为每个进程维护一个**页表（page table）**，本质上是个数组：`页表[虚拟页号] = 物理页号`。CPU 访问虚拟地址时：

1. 拆出虚拟页号 VPN。
2. 查页表得到物理页号 PPN。
3. 把 PPN 拼上原页内偏移，得到物理地址。
4. 用物理地址访问内存。

听起来简单，但有一个**致命问题**：页表本身放在内存里。每次访存都要先查页表（一次访存），再访问数据（再一次访存）——**翻一次地址要两次访存**！这把本来就慢的内存访问又翻了一倍。

#### 5.3 TLB：地址翻译的缓存

解决方案：**给页表查询本身做一个缓存**。这个缓存叫 **TLB（Translation Lookaside Buffer，转换后备缓冲器）**——CPU 内部一个非常小的全相联缓存，专门存最近用过的"虚拟页号→物理页号"映射。

CPU 访问虚拟地址时：

1. 先查 TLB——TLB 命中（hit）：直接拿到物理页号，无需访问页表。
2. TLB 未命中（miss）：才去内存查页表，把结果填回 TLB，再访问数据。

TLB 通常只有几十到几百个表项，但因为**访问也具有局部性**（程序往往在少数几个页内反复活动），TLB 命中率非常高，常常超过 99%。所以绝大多数地址翻译都在 TLB 里完成，不增加额外访存。这又是局部性原理的胜利。

#### 5.4 多级页表：地址空间太大怎么办

64 位地址空间下，如果页表是个简单的一维数组，光页表本身就要占用海量内存（哪怕大部分进程实际只用其中很小一部分）。所以现代系统用**多级页表**：把页表组织成树状结构，只有真正用到的部分才分配。

比如 x86-64 用 4 级页表：地址的高位被分成 4 段，分别索引 4 层页表。访问一次内存最坏情况要走 4 次页表（再加一次取数据，共 5 次访存）——这就是为什么 TLB 命中率如此关键，TLB miss 的代价非常昂贵。

多级页表的具体格式各 CPU 不同（x86-64、ARM64、RISC-V 各有规范），细节我不展开。重点是理解**用空间换时间和用时间换空间在这里再次出现**——多级页表用查询时间换内存占用。

### 六、亲手感受：用 C++ 测出缓存的存在

理论讲完了，我必须给你看一个实验。这个实验之所以重要，是因为它会让"缓存"从一个抽象概念变成你能亲手测到、亲眼看到的物理实在。

我会给你一段 C++ 代码，它通过一个简单的现象暴露 L1、L2、L3 缓存的存在和大小。

```cpp
#include <iostream>
#include <vector>
#include <chrono>
#include <cstdlib>

int main() {
    // 测试不同大小的数组，每个数组反复访问足够多次以稳定测量
    for (int size_kb = 4; size_kb <= 65536; size_kb *= 2) {
        size_t size = size_kb * 1024 / sizeof(int);
        std::vector<int> arr(size, 1);

        // 总访问次数固定（与数组大小无关），保证不同数组的总工作量一致
        const long long total_accesses = 100'000'000LL;
        long long iterations = total_accesses / size;
        if (iterations < 1) iterations = 1;

        // 跨步访问：每次跳一个缓存行（64 字节 = 16 个 int），
        // 这样每次访问都"很可能"是一个新的缓存行——能更清晰地体现缓存效应
        const int stride = 16;

        volatile long long sum = 0;  // volatile 防止编译器优化掉整个循环
        auto start = std::chrono::high_resolution_clock::now();

        for (long long it = 0; it < iterations; it++) {
            for (size_t i = 0; i < size; i += stride) {
                sum += arr[i];
            }

        auto end = std::chrono::high_resolution_clock::now();
        double ns = std::chrono::duration<double, std::nano>(end - start).count();
        double ns_per_access = ns / (iterations * (size / stride));

        std::cout << "Size: " << size_kb << " KB, "
                  << "ns per access: " << ns_per_access << "\n";
    }
    return 0;
}
```

在我的笔记本上跑这段代码，输出大致是这样的（具体数值因机器而异）：

```
Size: 4 KB,    ns per access: ~0.8     ← L1 内
Size: 16 KB,   ns per access: ~0.9     ← 仍在 L1 内
Size: 32 KB,   ns per access: ~1.0     ← L1 边缘
Size: 64 KB,   ns per access: ~3.2     ← 跌出 L1，进入 L2
Size: 128 KB,  ns per access: ~3.5
Size: 256 KB,  ns per access: ~3.8     ← L2 边缘
Size: 512 KB,  ns per access: ~10.5    ← 跌出 L2，进入 L3
Size: 4 MB,    ns per access: ~12.0
Size: 16 MB,   ns per access: ~30.0    ← 跌出 L3
Size: 64 MB,   ns per access: ~80.0    ← 完全在主存
```

请你认真凝视这组数字。**你看到了三个台阶**：从 ~1 ns 跳到 ~3 ns（L1→L2 边界），从 ~3 ns 跳到 ~10 ns（L2→L3 边界），从 ~10 ns 跳到 ~80 ns（L3→主存边界）。每个台阶的位置正好对应那台机器的 L1、L2、L3 大小。**缓存不再是 PPT 里的抽象概念，而是你亲手测到的、有边界、有延迟的物理实在**。

如果你有时间在自己的机器上跑这段代码，强烈建议跑一下——你会有一种"原来如此"的震撼感。

### 七、对你写代码的实战影响

最后这部分是最有用的。理解存储系统之后，你应该怎么写代码？

**第一，访问模式比算法复杂度更重要（在常数级别上）**。

经典的例子：链表 vs 数组。两者插入末尾都是 O(1)、查找都是 O(n)，但实际性能能差 10 倍以上。原因是数组在内存中连续，遍历时空间局部性极好，缓存预取（CPU 会自动把后续几个缓存行预先加载进来）更是雪上加霜地有效。链表节点散布在内存各处，每访问一个节点几乎都是 cache miss，每次 miss 要等约 100 ns。

竞赛圈有句老话："数组永远比链表快"——除了少数极端情况（比如频繁中间插入大量节点），这是对的。

**第二，二维数组的遍历方向至关重要**。

```cpp
// 方式 A：行优先（按行遍历）
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += arr[i][j];

// 方式 B：列优先
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += arr[i][j];
```

C/C++ 中二维数组按行存储（`arr[i][0], arr[i][1], ..., arr[i][N-1]` 在内存中连续）。**方式 A 沿连续内存遍历，每个缓存行能用满 16 次（如果是 int）；方式 B 每次访问都跳一行（跳 N×4 字节），N 大时几乎每次都 cache miss**。两种写法在 N=1000 左右时性能能差 5-10 倍——但 O 复杂度完全相同。

矩阵乘法、图像处理、卷积运算等，都对遍历方向极其敏感。这是写高性能代码的基本功。

**第三，结构体设计要考虑缓存对齐与紧凑性**。

```cpp
// 不好：字段顺序导致内存浪费
struct Bad {
    char  c1;     // 1 字节
    int   i;      // 4 字节，但前面要 padding 3 字节对齐到 4
    char  c2;     // 1 字节
    long  l;      // 8 字节，前面要 padding 7 字节对齐到 8
};                // 总共 24 字节

// 好：把大字段放前面
struct Good {
    long  l;      // 8 字节
    int   i;      // 4 字节
    char  c1;     // 1 字节
    char  c2;     // 1 字节
};                // 总共 16 字节（末尾 2 字节 padding）
```

紧凑的结构体每个缓存行能装更多对象，提高缓存利用率。

**第四，警惕"伪共享"**。在多线程程序中，如果两个线程频繁修改的两个变量恰好落在同一个缓存行（64 字节内），即使它们逻辑上无关，缓存一致性协议也会让两个线程的缓存反复失效，性能急剧下降。解决方法是把热点变量对齐到独立的缓存行（C++17 提供 `alignas(std::hardware_destructive_interference_size)`）。

**第五，循环内部尽量集中访问相关数据**（保持工作集小，最好能塞进 L1）。如果一个循环要访问的数据总量超过 L1 大小，考虑**分块（cache blocking）**——把大循环拆成小块，每块的数据能装进 L1。矩阵乘法的分块算法是经典案例，能把朴素实现加速十倍。

### 八、本讲小结与下讲预告

这一讲我们走过了存储系统的完整图景：

从**存储墙**这个根本矛盾出发——CPU 比内存快 300 倍，造成巨大鸿沟。看到了**局部性原理**这个让矛盾可解的关键观察——程序访问内存高度规律。基于此，构建了**存储层次结构**——用一系列容量递增、速度递减的存储器，让平均访问时间接近最快层。然后深入**缓存的具体设计**——以缓存行为单位、三种映射方式（直接、全相联、组相联）、替换策略（LRU 及其近似）、写策略（写直达、写回）、未命中类型（3C 模型）。然后上升到**虚拟内存**——通过分页和 TLB，给每个进程独立的、超过物理内存的虚拟地址空间。最后通过**实验**让你看到缓存的物理实在，并把这些理论转化为**写代码的具体指导**。

我希望你从这一讲带走三个核心认识。第一个是**层次化的近似**这个思想——我们没法造一个又快又大又便宜的存储器，但可以用一个金字塔式的层次结构，让"平均"接近理想。这种"用层次结构突破单点物理极限"的思路，在系统设计中无处不在。第二个是**局部性原理的可靠性**——它不是定理，但它如此普遍，以至于整个现代计算机系统都建立在它之上。当你写代码时，主动利用局部性（顺序访问、紧凑布局），就是在和现代硬件协作。第三个是**性能的真实来源往往不是 O 复杂度**——常数因子里藏着 10-100 倍的性能差，而这些差异主要来自缓存行为。理解了这一点，你写的代码会立刻变得快得多。
