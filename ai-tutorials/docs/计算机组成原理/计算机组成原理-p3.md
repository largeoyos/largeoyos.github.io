## 第四讲：指令系统——软硬件之间的契约

我们已经走过了三讲。第一讲讲了"数据是什么"，第二讲讲了"怎么对数据做运算"，第三讲讲了"数据存放在哪里"。这三讲解决的都是**机器内部**的问题——它们告诉你硬件是如何被组织起来的。但有一个根本问题我们还没有正面回答：**软件和硬件到底是怎么对话的？** 你写的 C++ 代码经过编译变成机器码，这串机器码怎么"驱动"硬件去做事？硬件凭什么"听懂"这串 0 和 1？

这个问题的答案，就是这一讲的主题：**指令集架构（Instruction Set Architecture，简称 ISA）**。

我希望你在听完这一讲之后，能够把"指令"这个词从一个模糊的术语变成一个清晰的、有结构的概念。你会知道一条指令在二进制层面长什么样、它如何被 CPU 解析、它能做什么不能做什么、为什么不同的 CPU 用不同的 ISA、以及为什么 RISC-V 在今天如此引人注目。这一讲也是我们在第五、六、七讲动手设计 CPU 之前的最后准备——理解了 ISA，CPU 设计就有了明确的目标。

### 一、ISA：一份契约，而不仅仅是一组指令

让我先给你一个稍微深一点的视角。很多教材把 ISA 直译为"指令集"，给人的感觉就是"一堆指令的列表"。这个理解不算错，但太肤浅了。我希望你换一个角度看：**ISA 是软件和硬件之间签订的一份契约**。

这份契约规定了什么？至少包括以下几个方面。它规定了 CPU 能识别哪些指令——比如有没有乘法指令、有没有原子操作指令。它规定了 CPU 内部有哪些"程序员可见"的状态——比如多少个寄存器，每个多少位，叫什么名字。它规定了内存如何寻址——地址是 32 位还是 64 位，按字节还是按字寻址，大端还是小端。它规定了指令在二进制层面的精确格式——哪几位是操作码，哪几位是寄存器编号，哪几位是立即数。它规定了异常和中断如何被处理——发生除零、缺页时 CPU 的行为。

这份契约的两侧是两个完全独立的工程团队。**软件方**（编译器、操作系统、应用程序的开发者）只看 ISA，不关心硬件具体怎么实现。他们的承诺是："我生成的机器码符合 ISA 规范"。**硬件方**（CPU 设计者）的承诺是："只要给我合法的机器码，我保证按 ISA 规定的语义执行"。至于硬件内部用单周期、流水线、乱序执行还是超标量——这是硬件的内部实现，软件不关心也不应该关心。

这种**接口与实现分离**的思想，使得 Intel 几十年来不断重新设计 x86 处理器的内部架构（从奔腾到酷睿再到现在的 Alder Lake，内部结构几代翻新），而你 1990 年代的 DOS 程序至今仍然能跑——因为 ISA 这份契约没变。同样，苹果 2020 年从 Intel 转向自研 ARM 芯片时，能用 Rosetta 2 在 ARM 硬件上模拟 x86 ISA，让旧软件继续运行——因为软件依赖的是 ISA，不是某块具体的芯片。

请你记住这个视角，因为它会帮助你理解后面所有的设计选择。**ISA 设计本质上是在设计一份契约，每一个决策都要考虑两侧的需求**。指令格式要"硬件好实现"也要"编译器好生成"；寄存器数量要"够编译器用"也要"硬件能装下"。这种双向的工程权衡，是 ISA 设计的核心张力。

### 二、CPU 内部的"程序员可见状态"

在讲指令本身之前，我们必须先弄清楚指令操作的对象是什么。CPU 内部有大量电路和状态，但其中只有一部分是 ISA 暴露给程序员的——也就是说，能被指令直接读写的。这部分叫**程序员可见状态（programmer-visible state）**或**架构状态（architectural state）**。

主要包括三类：通用寄存器、程序计数器、状态标志（以及一些特殊寄存器）。

**通用寄存器（General-Purpose Registers, GPR）** 是 CPU 内部一组小而极快的存储单元，每个能存一个机器字（32 位机器是 32 位，64 位机器是 64 位）。它们物理上就是上一讲说的"寄存器层级"——访问延迟通常小于 0.3 纳秒，比 L1 缓存还快几倍。指令的绝大多数操作都直接在寄存器之间进行——CPU 不会直接对内存做加法，而是先把数据装入寄存器、做加法、再把结果存回内存。

不同 ISA 的寄存器数量不同。x86-64 有 16 个通用寄存器（命名怪异：RAX、RBX、RCX、RDX、RSI、RDI、RBP、RSP、R8 到 R15，这是历史包袱），ARM64 有 31 个，RISC-V 有 32 个（命名整齐：x0 到 x31）。**寄存器数量是 ISA 设计的一个关键权衡**：太少会让编译器频繁地把变量"溢出"到内存（spilling），损失性能；太多会让指令编码需要更多位（要表示寄存器编号），同时增加上下文切换的成本（操作系统切换进程时要保存所有寄存器）。32 个是一个被广泛认可的甜点。

**程序计数器（Program Counter, PC）** 是一个特殊寄存器，里面存着"下一条要执行的指令的地址"。这是整个执行流程的指挥棒。CPU 的工作循环可以简化为这样：读 PC 指向的指令，执行它，更新 PC（顺序执行就是 PC + 4，因为指令通常 4 字节；遇到跳转指令则把 PC 改为目标地址）。这个循环叫**取指—译码—执行循环（fetch-decode-execute cycle）**，是冯·诺依曼机的灵魂。

PC 在不同 ISA 中暴露程度不同。在 ARM 里，PC 是一个普通寄存器（R15），可以被指令直接读写——比如 `MOV PC, R0` 就是跳转。在 x86 和 RISC-V 里，PC 是隐式的，不能像普通寄存器那样直接寻址，必须通过专门的跳转指令修改。这两种设计各有道理：ARM 的方式更统一（一切皆寄存器），但给编译器和硬件优化带来麻烦（PC 的修改是控制流变化，不能像普通寄存器那样自由调度）；x86/RISC-V 的方式更"诚实"地把控制流和数据流分开。

**状态标志（Flags）** 我们在第二讲讲过——零标志、符号标志、进位标志、溢出标志等。它们记录最近一次运算的状态，被后续的条件分支指令使用。x86 和 ARM 有显式的标志寄存器，而 **RISC-V 干脆取消了状态标志**——它没有专门的标志寄存器，条件分支直接比较两个寄存器的值（比如"如果 x1 等于 x2 就跳转"）。这是一个非常激进但有道理的设计，等下我会详细解释。

除了这三类，还有一些特殊寄存器：**栈指针（SP）** 指向当前函数栈的顶部；**帧指针（FP）** 用于函数调用约定（不是所有 ISA 都强制有）；各种**控制寄存器**用于操作系统级别的功能（页表基址、中断使能等）。这些细节因 ISA 而异，我们在用到时再展开。

理解这些"可见状态"的意义在于：**指令做的所有事情，最终都是改变这些状态**。一条加法指令把两个寄存器相加并把结果写入第三个寄存器；一条跳转指令把 PC 改成另一个地址；一条访存指令在寄存器和内存之间搬运数据。当我们看一段汇编代码时，本质上是在追踪"这些状态如何随时间演化"。这是阅读和理解汇编的基本心法。

### 三、指令的解剖：一条指令长什么样

现在我们走到最具体的层面：一条指令在二进制中究竟是什么样的？

每一条指令都是一串固定或可变长度的二进制位。CPU 拿到这串位之后，要从中解析出几样东西：**这是哪种操作？操作的对象是什么？操作的结果放哪里？** 这些信息被编码在指令的不同**字段（field）**中。最重要的字段是**操作码（opcode）**——它告诉 CPU 要做什么。其他字段则指定操作数。

我以 RISC-V 的加法指令为例，把这个过程具体展示一遍。考虑这条汇编：

```
add x10, x11, x12
```

它的语义是：把寄存器 x11 和 x12 的值相加，结果存入 x10。在 RISC-V 中，这条指令被编码为 32 位：

```
 funct7  |  rs2  |  rs1  | funct3 |  rd  | opcode
0000000  | 01100 | 01011 |  000   | 01010| 0110011
  7 位      5 位    5 位    3 位    5 位    7 位
```

让我们逐字段拆解。**opcode**（最低 7 位）是 `0110011`——这告诉 CPU "这是一条 R 型指令"（R-Type 表示寄存器到寄存器的运算）。**rd**（5 位）是 `01010` = 10——目标寄存器，所以结果会写入 x10。**funct3**（3 位）是 `000`——这是一个"次操作码"，配合 opcode 进一步指定具体运算（在 R 型 + opcode=0110011 的指令族里，funct3=000 意味着是加法或减法）。**rs1** 和 **rs2**（各 5 位）是源寄存器编号，分别是 11 和 12。**funct7**（最高 7 位）是 `0000000`——再一个次操作码，配合 funct3 区分加法（0000）和减法（0100000，第 30 位为 1）。

所以这一串看起来神秘的二进制 `0000000 01100 01011 000 01010 0110011`，被 CPU 解读为"把 x11 和 x12 相加，结果存入 x10"。每一位都有明确的语义，每一段都对应一个具体的硬件信号。

请你停下来想一想这个事实的奇妙之处：**整个软件世界——你的浏览器、操作系统、游戏、AI 模型——最终都是这样一串串的二进制，被 CPU 一条一条地解读和执行**。从 C++ 源码到这串二进制，中间隔着编译器、汇编器、链接器；但最终落到硬件上的，就是这种结构精确的位串。理解了这一点，整个计算机系统在你眼里就不再是黑箱。

#### 3.1 五种典型的指令格式

不同的指令需要不同的字段组合。比如加法用三个寄存器（两个源，一个目标），但跳转可能只需要一个目标地址，访存需要寄存器加偏移。RISC-V 把指令组织成**六种基本格式**，分别覆盖不同需求。我重点讲其中最常见的五种，因为它们覆盖了 90% 以上的指令。

**R 型（Register）**：寄存器到寄存器的运算。`add x10, x11, x12` 就是 R 型，三个寄存器编号都在指令中明确给出。

**I 型（Immediate）**：含有"立即数"（immediate，直接写在指令里的常数）的指令，比如 `addi x10, x11, 100`（把 x11 加上常数 100，结果存 x10）。立即数字段占 12 位。访存指令 `lw`（load word）也是 I 型——`lw x10, 8(x11)` 表示"从地址 x11+8 处读 4 字节装入 x10"，这里 8 就是立即数。

**S 型（Store）**：存储指令，比如 `sw x10, 8(x11)`（把 x10 写到内存地址 x11+8）。S 型和 I 型相似，但因为没有目标寄存器（数据从寄存器写到内存，不写回寄存器），立即数被分成两段插在不同位置——这是为了硬件解码方便（让 rs1 和 rs2 字段在 R/I/S 型里始终在同一位置）。

**B 型（Branch）**：条件分支指令，比如 `beq x10, x11, label`（如果 x10 等于 x11 就跳到 label）。B 型也有立即数（跳转的偏移量），同样分段编码。

**U 型（Upper immediate）**：用于加载大立即数的指令。因为 I 型的立即数只有 12 位，要装入一个 32 位常数需要分两步：先用 U 型指令 `lui` 装入高 20 位，再用 I 型指令 `addi` 加上低 12 位。这看起来麻烦，但反映了"指令长度有限，必须妥协"的现实。

**J 型（Jump）**：无条件跳转，比如 `jal x1, label`（跳到 label，把返回地址存入 x1，用于函数调用）。立即数字段达 20 位，能跳得更远。

这六种格式设计得**极为对称**：寄存器字段（rs1、rs2、rd）只要存在就都在固定的位置；立即数字段虽然在不同格式里被分段，但分段方式经过精心设计——硬件解码时，无论指令是哪种格式，提取立即数的电路路径都很短。这种"硬件友好"的对称性是 RISC-V 区别于 x86 的关键设计哲学之一。x86 因为历史原因，指令格式极其混乱，长度从 1 字节到 15 字节不等，解码器要花费大量晶体管。

#### 3.2 指令的语义描述

光看二进制布局还不够，我们还需要一种**简洁的方式描述每条指令的语义**。教材里常用所谓的**寄存器传输级（Register Transfer Level, RTL）** 表示法，它把指令的效果写成一组形如"目的 ← 源"的赋值。

比如 `add x10, x11, x12` 的 RTL 描述是：

x10leftarrowx11+x12

`lw x10, 8(x11)` 的 RTL 描述是：

x10leftarrowtextMem[x11+8]x10leftarrowtextMem[x11+8]

`beq x10, x11, label` 的 RTL 描述是：

textif(x10==x11)textthenPCleftarrowPC+textoffset

这种表示法在第五讲设计 CPU 时会大量使用——它正好对应硬件中"寄存器之间的数据流动"，写出 RTL 等于写出了硬件应该做什么的精确规格。

### 四、寻址方式：怎么找到操作数

操作数可能在寄存器里，也可能在内存里，还可能直接是一个常数。指令通过不同的**寻址方式（addressing mode）** 来指定操作数的位置。常见的寻址方式有这几种：

**立即数寻址**：操作数直接写在指令里。`addi x10, x11, 100` 中的 100。优点是不用访问任何存储；缺点是立即数大小受限于指令字段宽度。

**寄存器寻址**：操作数在寄存器里，指令给出寄存器编号。这是 RISC 架构最主流的方式——大多数运算指令的操作数都来自寄存器。

**直接寻址**：指令中直接给出内存地址。比如某些 CISC 指令可以写 `MOV AX, [0x1000]`（把内存地址 0x1000 处的值装入 AX）。这种方式简单但不灵活——地址必须是编译时已知的常数。

**寄存器间接寻址**：内存地址在寄存器里。`lw x10, 0(x11)` 就是这种——把 x11 当作指针，访问它指向的内存。这是实现 C 语言指针、数组下标的关键。

**基址加偏移寻址**：上面那种的扩展，把寄存器值加上一个立即数偏移作为内存地址。`lw x10, 8(x11)` 访问地址 x11+8。**这是访问结构体成员、栈帧局部变量的标准方式**——比如 C 里 `obj->field` 编译后通常就是 "把 obj 装入寄存器，然后用基址+偏移访问 field"。

**变址寻址**和**相对寻址**：x86 还支持更复杂的形式，比如 `[base + index*scale + disp]`（基址寄存器 + 变址寄存器*比例 + 偏移）。这种"一条指令完成数组元素地址计算"的设计是 CISC 风格——硬件复杂但代码紧凑。RISC-V 不直接支持这种，需要用多条指令实现。

寻址方式的多寡，是 RISC 与 CISC 哲学差异的一个具体体现。RISC 倾向于少而精的寻址方式（RISC-V 主要就只有立即数、寄存器、基址加偏移这三种），让硬件简单；CISC 倾向于丰富的寻址方式（x86 有十几种），让代码紧凑。两种思路各有道理，下一节我们正面对比。

### 五、RISC vs CISC：两种设计哲学的世纪之争

ISA 的设计史上有一场持续了四十年的论战：**复杂指令集（CISC, Complex Instruction Set Computer）** 和**精简指令集（RISC, Reduced Instruction Set Computer）** 哪个更好？

#### 5.1 CISC 的逻辑

CISC 的代表是 x86。它的设计哲学是：**让指令尽可能强大，一条指令做尽可能多的事**。x86 里有这样的指令：

`REP MOVSB`：把一段内存复制到另一段，长度由寄存器决定。这一条指令能做 C 里 `memcpy` 的事。

`LOOP`：把计数器减 1，如果不为零就跳转。一条指令完成"循环判断+跳转"。

`STRING` 系列指令：对字符串进行各种操作。

CISC 这样设计的历史背景是 1970 年代——那时候编译器还不发达，很多程序是手写汇编的；同时内存非常昂贵，代码越紧凑越好。复杂指令既能让汇编程序员少写几行，又能让程序占用更少的存储空间。

CISC 的特征通常包括：指令数量多（x86 有上千条指令）、指令长度可变（从 1 字节到 15 字节）、寻址方式丰富、指令可以直接操作内存（不用先 load 到寄存器）、指令执行时间不一（有的一周期，有的几十周期）。

#### 5.2 RISC 的反叛

1980 年代，加州大学伯克利分校（David Patterson）和斯坦福大学（John Hennessy）的研究者们提出了一个挑战 CISC 的观点——你猜怎么着，**真实程序里 CISC 那些复杂指令根本很少被用到**。统计显示编译器生成的代码 90% 以上由"简单指令"构成，那些华丽的复杂指令大多躺在指令集手册里吃灰。

更糟的是，**复杂指令拖慢了所有指令**。CPU 内部要支持各种复杂指令，解码器、控制器都得做得很复杂，导致简单指令也跑不快。这就像一个万能瑞士军刀因为塞了太多功能反而每个功能都做得不好。

RISC 的核心主张：**让指令简单、统一、规整，让常用的事情高效，不常用的事情让编译器用多条简单指令拼出来**。具体特征：指令数量少（RISC-V 基础指令集只有 47 条）、指令长度统一（都是 32 位）、只有 load/store 指令能访问内存（其他指令只能在寄存器间运算，所以叫**load-store 架构**）、寻址方式简单、每条指令尽量在一个时钟周期完成。

RISC 的代表是 MIPS、SPARC、PowerPC、ARM、RISC-V。

#### 5.3 对决与融合

这场论战有过几个回合。1990 年代初 RISC 看似赢了——RISC 处理器在科学计算和服务器领域大放异彩。但 Intel 没有束手就擒：从 Pentium Pro 开始，x86 处理器内部其实是 RISC 的——CPU 解码器把 CISC 指令翻译成内部的"微操作（micro-ops，简称 μops）"，每个微操作是 RISC 风格的简单指令。这样 x86 在外部仍然是 CISC（保持软件兼容），内部却是 RISC（享受高性能）。这是一个非常聪明的折中。

所以今天 RISC vs CISC 的界限其实模糊了。x86 表面是 CISC 但内核是 RISC；ARM 加了越来越多的指令变得不那么"精简"。但**精神上 RISC 赢了**——所有现代高性能 CPU 内部都用 RISC 风格的简单微操作工作。

#### 5.4 几个具体的设计差异

为了让你具体感受，我列几个 RISC-V 和 x86 的对比。

**寄存器间接 vs 复杂寻址**。给定一个数组求和的 C 代码：

```c
int sum = 0;
for (int i = 0; i < n; i++) sum += a[i];
```

x86 可以用一条指令 `add eax, [rsi + rcx*4]` 完成"读取 a[i] 并加到 sum"——这条指令包含了内存读取和加法两个操作。RISC-V 必须分两步：`lw t0, 0(s0)` 读取，`add s1, s1, t0` 相加。看起来 x86 更简洁，但 RISC-V 的两条指令各自只做一件事，硬件流水线更容易处理；x86 的复杂指令在内部会被拆成几个 μops 执行，本质上是同样的事，只是封装方式不同。

**条件分支的方式**。x86 的条件分支依赖标志寄存器：先用 `CMP` 或某个算术指令设置标志，再用 `JE`、`JL`、`JG` 等根据标志跳转。这是两条指令的耦合。RISC-V 没有标志寄存器，条件分支直接比较两个寄存器：`beq x10, x11, label`（相等就跳）、`blt x10, x11, label`（小于就跳）。这是单条指令的事，且语义自包含——硬件流水线中不需要追踪标志寄存器的依赖，简化了乱序执行的实现。

**指令长度**。x86 指令 1-15 字节不等，解码器必须先看第一个字节，决定指令长度，再读取后续字节——而且还要支持各种前缀字节修改指令含义。这导致 x86 的解码器极其复杂，是 CPU 内部最大的功耗黑洞之一。RISC-V 标准指令统一 32 位，第一个字节就能确定边界，多条指令甚至可以并行解码。

每一个差异都体现着 RISC 的"硬件简单、编译器努力"和 CISC 的"硬件强大、汇编程序员/早期编译器轻松"的根本分歧。

### 六、为什么是 RISC-V

我已经几次提到要"以 RISC-V 为主线"。现在我解释为什么——这不仅是教学考虑，也反映了一个真实的产业趋势。

**RISC-V** 是 2010 年由加州大学伯克利分校（同一群当年提出 RISC 的人）发起的开源指令集架构。这是一个非常重要的事实：**RISC-V 是免费且开放的，任何人都可以实现 RISC-V 处理器而无需缴纳授权费**。相比之下，x86 由 Intel 和 AMD 控制（有高额授权门槛），ARM 由 Arm 公司授权（每用一次都要交钱）。

RISC-V 的设计借鉴了几十年来 RISC 的全部经验教训，干净到几乎"教科书化"。它有几个突出特征：

**模块化设计**。RISC-V 不是一个单一指令集，而是一个"基础 + 扩展"的体系。基础指令集叫 RV32I（32 位整数）或 RV64I（64 位整数），只有 47 条指令——简单到一个学期能完整学完。扩展用字母标识：M 表示乘除（Multiply）、F/D 表示单/双精度浮点、A 表示原子操作（Atomic）、C 表示压缩指令（Compressed，16 位短指令）、V 表示向量（Vector）。一颗芯片实现哪些扩展，根据用途选择——嵌入式微控制器可能只要 RV32IC，服务器 CPU 可能要 RV64IMAFDCV。这种模块化让 RISC-V 既能做最简单的物联网芯片，也能做最复杂的高性能处理器。

**为现代设计而生**。RISC-V 没有历史包袱，所有设计选择都是基于当代经验的。32 个通用寄存器（包括硬连线为 0 的 x0，简化了很多操作的实现）、统一 32 位指令、严格 load-store、无标志寄存器、支持 64 位虚拟地址、内置对虚拟化和多核的支持——每一项都反映了"RISC 第二代"的成熟思考。

**正在迅速崛起**。RISC-V 已经被许多公司采用：阿里巴巴的玄铁系列、SiFive 的处理器、谷歌的部分内部芯片、英伟达 GPU 的微控制器。中国因为受 x86 和 ARM 的限制，对 RISC-V 投入巨大——这对你这个专业的就业前景有切实意义。学界也在快速转向 RISC-V，伯克利、斯坦福、CMU 的计组课程基本都在用它替代 MIPS 作为教学 ISA。

**对教学最友好**。MIPS 曾经是教学黄金标准（Patterson 和 Hennessy 的经典教材《计算机组成与设计》早期版本就用 MIPS），但 MIPS 商业上已基本消亡。RISC-V 不仅在教学上同样清晰，还有完整的工业生态——你学完它直接可以用真实的工具链（GCC、QEMU 都支持 RISC-V）写代码、跑在真实的硅片上。这种"教学和实战零距离"是无价的。

所以接下来设计 CPU 时，我们就以 RISC-V 的 RV32I 为目标 ISA。它的简洁性会让我们专注于 CPU 设计本身，而不是被指令集的细节淹没。

### 七、一段简单 C 代码的指令视角

为了把这一讲所有内容串起来，我让你看一段简单的 C 代码以及它编译后的 RISC-V 汇编。

```c
int sum_array(int *arr, int n) {
    int sum = 0;
    for (int i = 0; i < n; i++) {
        sum += arr[i];
    }
    return sum;
}
```

编译后的 RISC-V 汇编大致是这样的（简化版）：

asm

```asm
sum_array:
    li   t0, 0          # t0 = 0  （这是 sum，对应 C 里的 sum=0）
    li   t1, 0          # t1 = 0  （这是 i）
loop:
    bge  t1, a1, end    # 如果 t1 >= a1（即 i >= n）就跳到 end
    slli t2, t1, 2      # t2 = t1 << 2，即 i*4（int 是 4 字节）
    add  t3, a0, t2     # t3 = a0 + t2，即 &arr[i]（基址 + 偏移）
    lw   t4, 0(t3)      # t4 = Mem[t3]，即读取 arr[i]
    add  t0, t0, t4     # t0 = t0 + t4，即 sum += arr[i]
    addi t1, t1, 1      # t1 = t1 + 1，即 i++
    j    loop           # 无条件跳回 loop
end:
    mv   a0, t0         # 返回值放在 a0 寄存器
    ret                 # 返回（实际是 jalr x0, 0(ra)）
```

请你认真读一遍这段汇编。**每一行都对应这一讲讲过的某个概念**：`li` 是加载立即数（U 型 + I 型组合），`bge` 是 B 型条件分支（无标志寄存器，直接比较），`slli` 是 I 型立即数移位，`add` 是 R 型寄存器加法，`lw` 是 I 型基址加偏移访存，`j` 是 J 型无条件跳转。函数参数通过约定的寄存器传递（a0 是第一个参数，a1 是第二个，返回值也在 a0）——这种"调用约定（calling convention）" 是 ISA 之上的进一步约定，让不同编译器编译的代码能互相调用。

整个函数的执行过程，本质上就是 CPU 不断地"读取 PC 指向的指令、解码、执行、更新 PC"的循环。每一次循环都让某些寄存器或内存的状态发生确定的、可预测的变化。这就是计算的本质——**离散的状态变化序列**。

我希望这段简单代码让你看到：**从 C 到汇编再到机器码，这个翻译过程是机械的、规则的、可理解的。它不是黑魔法**。当你看一段汇编时，你看到的是 CPU 执行轨迹的逐步展开——每条指令的语义清晰、状态变化明确。

### 八、本讲小结与下讲预告

这一讲我们走过了 ISA 的全景：

我们从把 ISA 理解为**软硬件之间的契约**开始——它规定了两侧的接口，让独立演化的硬件和软件能够协作。然后看了 CPU 的**程序员可见状态**——通用寄存器、PC、状态标志，这些是指令操作的对象。接着我们解剖了**一条指令的二进制结构**——以 RISC-V 的 R 型加法为例，看到了 opcode、寄存器字段、立即数字段如何被精心组织。然后概览了 RISC-V 的**六种指令格式**和它的**对称设计哲学**。我们讨论了不同的**寻址方式**，并在 **RISC vs CISC 之争**中看到了两种设计哲学的根本分歧及最终融合。最后我们解释了为什么以 **RISC-V** 为学习主线，并通过一段 C 代码到汇编的翻译，把所有概念串了起来。

我希望你从这一讲带走三个核心观念。第一个是 **ISA 是契约**——这个视角让你理解为什么 ISA 设计如此谨慎、为什么 ISA 改变如此罕见、为什么软件能在硬件迭代中保持兼容。第二个是 **指令是状态变换的描述**——每条指令做的事情就是按规则改变寄存器、内存、PC 的值；理解了这一点，阅读汇编就成了追踪状态演化的过程。第三个是 **简单优于复杂**——RISC 的胜利说明了一个深刻的工程教训：让常用的事情快是值得的，让所有事情都"看起来强大"反而会拖累整体。这个教训不仅适用于 CPU 设计，也适用于你将来设计任何系统。

下一讲我们进入这门课的高潮：**第五讲：单周期 CPU 设计**。我们将把前四讲学到的所有东西——数据表示、ALU、寄存器、内存、指令格式——拼装成一台真正能工作的 CPU。我们会画出**数据通路（datapath）**——CPU 内部所有部件如何用导线连接；会设计**控制单元（control unit）**——它如何根据当前指令产生控制信号，让数据通路做正确的事；会用 Verilog 风格的代码描述每一个模块。这一讲之后，你会真切地理解"CPU 是怎么造出来的"，从此再看任何 CPU 框图都不会陌生。

## 第五讲：单周期 CPU 设计——把所有部件拼成一台机器

我们终于走到了这门课的核心。前四讲我们准备了所有的"零件"：第一讲我们知道了数据是 0 和 1 的串；第二讲我们造出了 ALU，能对这些串做运算；第三讲我们理解了存储系统，知道数据从哪里来到哪里去；第四讲我们学会了指令集，知道如何用一份契约让软件指挥硬件。现在，我们要把这些零件拼装成一台真正能工作的 CPU。

我希望你在听完这一讲之后，能够**亲手画出一台 CPU 的完整数据通路**，并且对每一根导线、每一个部件的作用都心知肚明。当你将来再看到任何处理器的架构图——无论是教材里的示意图还是真实芯片的框图——你都能一眼认出"这是 PC，这是寄存器堆，这是 ALU，这是控制单元"。这种能力一旦建立起来，就再也不会失去。

这一讲我会按这样的顺序展开：先建立 CPU 工作的总体节奏——取指、译码、执行、访存、写回这五个阶段；然后按照阶段顺序，逐步设计每个阶段需要的硬件部件；接着把所有部件用导线连接起来形成完整的数据通路；最后设计控制单元，让数据通路在不同指令下做不同的事。整个过程会以 RISC-V 的 RV32I 指令集为目标——它简洁规整，是教学的理想选择。

### 一、CPU 工作的五个阶段

让我们先建立一个最高层的画面。CPU 在执行任何一条指令时，从概念上都要经过五个阶段。这不是某个具体设计的特殊性，而是冯·诺依曼体系结构的本质要求——任何执行指令的机器都必须做这些事情。

第一个阶段叫**取指（Instruction Fetch, IF）**。CPU 根据 PC 的值，从指令存储器中读出当前要执行的指令。这一步就像你读一本书时眼睛扫到当前那一行——你必须先把字"看到"，才谈得上理解和行动。取指阶段结束时，CPU 手里有了一串 32 位的二进制（对于 RISC-V），但它还不知道这串二进制具体要它做什么。

第二个阶段叫**译码（Instruction Decode, ID）**。CPU 把刚取到的指令拆开，识别出它的操作码、源寄存器编号、目标寄存器编号、立即数等字段。这一步就像你读到一行字之后理解它的语法结构——"这是个 add 指令，它要把 x11 和 x12 相加，结果存到 x10"。译码阶段还包括从寄存器堆中读出源寄存器的值，这样后续阶段就有了实际的数据可以操作。

第三个阶段叫**执行（Execute, EX）**。CPU 把源操作数送进 ALU，根据指令类型让 ALU 做相应的运算——加法指令做加法，减法指令做减法，比较指令做比较。对于访存指令，这一阶段计算访问内存的地址（基址加偏移）；对于分支指令，这一阶段判断是否要跳转。这是 CPU 真正"动脑"的阶段。

第四个阶段叫**访存（Memory Access, MEM）**。如果当前指令是 load（如 `lw`），CPU 用执行阶段算出的地址去访问数据存储器，读出数据；如果是 store（如 `sw`），CPU 把寄存器的值写入指定地址。对于既不读也不写内存的指令（比如纯计算的 `add`），这一阶段什么也不做——但它仍然存在，因为 CPU 的工作节奏是统一的。

第五个阶段叫**写回（Write Back, WB）**。如果当前指令需要把结果写入某个寄存器（绝大多数指令都需要），这一阶段把结果写入寄存器堆中由 rd 字段指定的位置。同时，PC 被更新——通常是 PC + 4（指向下一条指令），但分支或跳转指令会把 PC 改成目标地址。

请你在脑子里建立这张图：**指令进入 CPU，依次经过取指、译码、执行、访存、写回五个工位，每经过一个工位就被"加工"一次，最后从写回工位出来时，整个 CPU 的状态（寄存器、内存、PC）已经按指令的语义完成了更新**。这就是 CPU 工作的节奏。

现在有一个关键问题：**这五个阶段是依次串行的，还是可以重叠？** 这个问题的不同答案决定了 CPU 的不同设计风格。**单周期 CPU**——也就是这一讲的主题——的回答是"严格串行"：每条指令在一个时钟周期内完整地走完所有五个阶段，下一个时钟周期才开始下一条指令。**流水线 CPU**（下一讲的主题）的回答是"重叠执行"：让多条指令同时在不同阶段中流动，就像工厂的装配线一样。我们先把单周期搞清楚，因为它是流水线设计的基础。

### 二、关键部件清单

在动手设计之前，我们需要先列出一台单周期 CPU 必须包含的关键部件。让我把它们一个一个介绍清楚。

**程序计数器（PC）** 是一个 32 位的寄存器，里面存着当前要执行的指令的地址。它在每个时钟周期的末尾被更新——对于顺序执行的指令，新值是旧值加 4；对于跳转指令，新值是跳转目标。PC 是时序逻辑的典型例子——它有"记忆"，必须在时钟边沿更新。

**指令存储器（Instruction Memory）** 存放程序的机器码。它是一个简单的存储器：给一个地址（来自 PC），返回该地址处的 32 位指令。在真实的 CPU 中，这部分由 L1 指令缓存实现；在我们的教学设计中，可以简化为一个理想的存储器，访问立即返回。

**寄存器堆（Register File）** 是 32 个 32 位寄存器的集合，对应 RISC-V 的 x0 到 x31。它需要支持同时读两个寄存器（提供两个源操作数）和写一个寄存器（写回结果），所以它有两个读端口和一个写端口。注意一个特别的设计：**x0 永远读出 0，写入它无效**——这是 RISC-V 的硬件约定，让"清零"、"无操作"等用法可以用统一的指令格式表达。

**算术逻辑单元（ALU）** 我们在第二讲已经详细造过了。它接收两个 32 位操作数和一个操作选择信号，输出运算结果以及状态标志（特别是 zero 标志，用于条件分支判断）。

**数据存储器（Data Memory）** 存放程序运行时的数据。和指令存储器类似，它有读地址、读数据、写地址、写数据等端口。在真实 CPU 中由 L1 数据缓存实现；这里也简化处理。把指令和数据分开成两个存储器的设计叫**哈佛架构**——它和"统一存储器"的**冯·诺依曼架构**是两种风格，现代 CPU 通常在 L1 层用哈佛架构（指令缓存和数据缓存分离），在更下层用冯·诺依曼架构（共享）。

**立即数生成器（Immediate Generator）** 是一个组合逻辑模块，专门负责把指令中分散的立即数字段重新组合成一个完整的 32 位立即数。还记得第四讲讲过的吗——RISC-V 的不同指令格式（I 型、S 型、B 型、U 型、J 型）把立即数放在不同的位置且分段存储，立即数生成器就是把这些片段拼回来的电路。它的输入是 32 位指令，输出是 32 位扩展后的立即数。

**多路选择器（Multiplexer，简称 MUX）** 是一个简单但极其重要的部件。它有多个输入和一个输出，由一个选择信号决定把哪个输入送到输出。MUX 在 CPU 中无处不在——任何"在多个数据源中选一个"的场合都要用它。比如 ALU 的第二个输入有时来自寄存器（R 型指令），有时来自立即数（I 型指令），就需要一个 MUX 在两者之间选择。

**符号扩展器**虽然在 RISC-V 中通常已经被立即数生成器吸收了，但它的概念值得单独提一下：把一个较短的有符号数扩展为较长的位宽时，要把符号位（最高位）复制到所有新增的高位上。比如把 12 位的立即数 `0xFFF`（即 -1）扩展为 32 位时，结果应该是 `0xFFFFFFFF`（仍然是 -1）；而扩展 `0x001`（即 1）时，结果应该是 `0x00000001`（仍然是 1）。这就是为什么叫"符号扩展"——保持有符号数的值不变。

这八类部件就是单周期 CPU 的全部硬件了。是不是比想象中少？**整个 CPU 的复杂性不在于部件多，而在于它们如何被组织起来协同工作**。下一节我们就开始这种组织。

### 三、按指令类型分别设计数据通路

这里我用一个非常有效的教学策略——**不要一上来就画完整的数据通路图，那样会让你淹没在导线的海洋里**。相反，我们按指令类型一个一个来：先看 R 型指令需要怎样的数据通路，再看 I 型指令、load、store、分支、跳转。每加一种指令就给已有的数据通路扩充一点。最后所有指令的需求叠加在一起，就是完整的数据通路。

#### 3.1 R 型指令的数据通路

我们从最简单的 R 型指令开始，比如 `add x10, x11, x12`。它要做的事情用 RTL 描述是：

x10leftarrowx11+x12PCleftarrowPC+4

让我们顺着五个阶段走一遍。

**取指阶段**。PC 提供地址给指令存储器，指令存储器返回 32 位指令。同时，PC 加 4（用一个专门的加法器，不要和 ALU 混淆——这是教学设计中常见的小加法器）准备作为下一周期的 PC 值。

**译码阶段**。从指令的 rs1 字段（位 19-15）取出 11，从 rs2 字段（位 24-20）取出 12，从 rd 字段（位 11-7）取出 10。把 rs1=11、rs2=12 送进寄存器堆的两个读端口，寄存器堆同时返回 x11 和 x12 的值。

**执行阶段**。把 x11 和 x12 的值送进 ALU 的两个输入，ALU 操作选择信号设为"加法"，ALU 输出 x11 + x12 的结果。

**访存阶段**。R 型指令不访问内存，这一阶段无操作。

**写回阶段**。把 ALU 的结果写入寄存器堆的写端口，写地址是 rd=10。同时 PC 被更新为之前算好的 PC+4。

把这些操作画成框图，就是 R 型指令的数据通路。我用文字描述给你建立画面：左上角是 PC，连到指令存储器；指令存储器输出 32 位指令，指令的不同字段（rs1、rs2、rd）连到寄存器堆的对应端口；寄存器堆的两个读出值连到 ALU 的两个输入；ALU 的输出连回寄存器堆的写端口。同时有一个独立的加法器算 PC+4，结果连回 PC。

#### 3.2 I 型算术指令的扩展

接下来加入 I 型算术指令，比如 `addi x10, x11, 100`。它的 RTL 是：

x10leftarrowx11+100

和 R 型几乎一样，唯一的区别是**ALU 的第二个输入不是 rs2 寄存器的值，而是立即数 100**。

这就需要在 ALU 的第二个输入前加一个 MUX：当前指令是 R 型时，MUX 选择寄存器堆的第二个读出值；当前指令是 I 型时，MUX 选择立即数生成器的输出。这个选择由控制信号决定（我们暂时把它叫做 `ALUSrc`）。

```verilog
// 概念性 Verilog 片段：ALU 第二个输入的 MUX
wire [31:0] alu_input_b = ALUSrc ? immediate : reg_read_data2;
//                          ^控制信号       ^I型时选这个    ^R型时选这个
```

这就是数据通路演化的方式——**新加一种指令，往往就是在某个位置加一个 MUX**。每个 MUX 由一个控制信号驱动；所有控制信号最终由控制单元产生（我们等下会讲）。

#### 3.3 Load 指令的扩展

现在加入 load 指令，比如 `lw x10, 8(x11)`，它的 RTL 是：

x10leftarrowtextMem[x11+8]x10leftarrowtextMem[x11+8]

让我们分析它在每个阶段需要什么。译码阶段从指令中提取 rs1=11、rd=10、立即数=8。执行阶段需要让 ALU 算 x11 + 8——这正好就是 I 型算术指令的模式（ALU 第二输入是立即数）。访存阶段用 ALU 的输出作为地址访问数据存储器，读出数据。写回阶段把读出的数据写入 x10。

新增的需求是什么？**写回阶段写入寄存器的数据，对于 R 型和 I 型算术指令是 ALU 的输出，对于 load 指令是数据存储器的输出**——所以寄存器堆的写数据端口前面也需要一个 MUX：

```verilog
// 写回数据的 MUX
wire [31:0] write_back_data = MemToReg ? mem_read_data : alu_result;
//                              ^控制信号    ^load 时选内存数据   ^其他时选 ALU 结果
```

控制信号 `MemToReg` 在 load 指令时为 1，其他指令为 0。

#### 3.4 Store 指令的扩展

接下来是 store，比如 `sw x10, 8(x11)`，RTL 是：

textMem[x11+8]leftarrowx10textMem[x11+8]leftarrowx10

注意这里 x10 是要被存到内存的数据，x11 + 8 是地址。在 RISC-V 的 S 型指令编码中，rs1（基址寄存器）是 x11，rs2（要存的数据）是 x10——也就是说**寄存器堆的两个读端口都被用上了**：第一个读出 x11 给 ALU 算地址，第二个读出 x10 作为要写入内存的数据。

新增的需求：**数据存储器需要一个写端口**，控制信号 `MemWrite` 在 store 指令时为 1，使能写入。同时，store 指令不写回寄存器，所以寄存器堆的写使能信号 `RegWrite` 在 store 时应为 0。

到这里我们已经覆盖了 R 型、I 型算术、load、store 四类指令——这已经是大多数日常计算的主体。让我们继续。

#### 3.5 分支指令的扩展

分支指令带来了**控制流**的复杂性。考虑 `beq x10, x11, label`，它的 RTL 是：

textif(x10==x11)textthenPCleftarrowPC+textoffsettextelsePCleftarrowPC+4

需要做两件事。第一是**判断条件**：把 x10 和 x11 送进 ALU 做减法，看 zero 标志。如果 zero=1（结果为 0），说明两者相等，条件成立。第二是**计算跳转目标**：当前 PC 加上立即数 offset（B 型指令的立即数）。这需要一个新的加法器（不是 ALU，也不是 PC+4 加法器，而是第三个加法器——专门算 PC + offset）。

新增的需求：**PC 的下一个值不再总是 PC+4，而是 PC+4 或 PC+offset 二选一**——又一个 MUX！这个 MUX 由一个特殊的控制信号驱动，姑且叫它 `PCSrc`。它由两个东西共同决定：当前指令是不是分支指令（控制信号 `Branch`），以及条件是否成立（ALU 的 zero 标志）。

```verilog
wire PCSrc = Branch & zero;  // 分支指令 且 条件成立
wire [31:0] next_pc = PCSrc ? (pc + branch_offset) : (pc + 4);
```

这是数据通路中第一次出现"条件性的控制流变更"——也是 CPU 真正区别于一个纯组合逻辑电路的地方。

#### 3.6 跳转指令的扩展

最后是无条件跳转，比如 `jal x1, label`（jump and link），它的 RTL 是：

x1leftarrowPC+4PCleftarrowPC+textoffset

注意它做了两件事：把返回地址（PC+4）存到目标寄存器（这就是为什么叫"link"，用于函数调用），同时跳到目标地址。

数据通路上需要的扩展：**写回寄存器的数据多了一种来源——PC+4**。所以那个写回数据的 MUX 从二选一变成了三选一（ALU 输出、内存数据、PC+4）。同时，PC 的下一个值也多了一种可能——`jal` 是无条件跳转，不依赖 zero 标志，所以 PCSrc 的逻辑也要扩展。

到这里，所有主要指令类型都覆盖了。让我们把所有的扩展叠加起来。

### 四、完整的单周期数据通路

经过上面六轮迭代，完整的单周期数据通路包含以下连接关系。我用文字详细描述，请你边读边在脑子里（或者真的拿张纸）把它画出来——这个练习对建立直觉极其重要。

整个数据通路可以从左向右画，大致分为五个垂直的"区域"，对应五个阶段。

**最左边是取指区域**。PC 寄存器在最上方，它的输出连到指令存储器的地址输入。指令存储器的输出（32 位指令）向右流动，进入译码区域。同时 PC 的输出还连到一个加法器（PC+4 加法器），加法器的另一个输入是常数 4，输出连到 PC 更新逻辑（最终通过一个 MUX 决定 PC 的下一个值）。

**译码区域**包含寄存器堆和立即数生成器。指令的 rs1 字段（位 19-15）连到寄存器堆的读地址 1，rs2 字段（位 24-20）连到读地址 2，rd 字段（位 11-7）连到写地址。寄存器堆有两个读出端口（输出 x[rs1] 和 x[rs2]），向右流入执行区域。立即数生成器以整条指令为输入（因为不同格式的立即数位置不同，需要看 opcode 才知道怎么提取），输出 32 位扩展后的立即数，也向右流入执行区域。

**执行区域**的核心是 ALU。ALU 的第一个输入直接来自寄存器堆的读出端口 1（x[rs1] 的值）。ALU 的第二个输入前面有一个 MUX——它在寄存器堆的读出端口 2（x[rs2]）和立即数生成器的输出之间二选一，由控制信号 ALUSrc 决定。ALU 的操作选择信号来自控制单元（我们等下细讲）。ALU 输出运算结果，并产生 zero 标志。同时，**这个区域还有一个独立的加法器**专门算 PC + offset（用于分支和跳转的目标地址），它的两个输入分别是 PC 和立即数生成器的输出。

**访存区域**包含数据存储器。数据存储器的地址输入来自 ALU 的输出（因为 load/store 用 ALU 算地址）。它的写数据输入来自寄存器堆的读出端口 2（也就是 x[rs2]，因为 S 型指令中 rs2 存的是要写入内存的数据）。它的读数据输出向右进入写回区域。控制信号 MemRead 和 MemWrite 分别使能读和写。

**写回区域**就是一个三选一的 MUX——它在 ALU 输出、数据存储器输出、PC+4 三者之间选择，决定写入寄存器堆的数据。这个 MUX 的输出连回寄存器堆的写数据端口。控制信号 MemToReg（或者更通用一些叫 WBSrc）决定选哪个。

最后是**PC 更新逻辑**。PC 的下一个值由一个 MUX 决定，它在 PC+4（来自取指区域的加法器）和 PC+offset（来自执行区域的第三个加法器）之间选择，由控制信号 PCSrc 决定。每个时钟上升沿，PC 寄存器锁存这个新值。

请你在脑子里完整跑一遍这个流程：一条 32 位指令从 PC 出发，经过指令存储器进入译码，分流到寄存器堆和立即数生成器，结果汇集到 ALU 进行运算，可能去访问数据存储器，最终结果通过 MUX 选择后写回寄存器堆，同时 PC 被更新。**整个过程在一个时钟周期内完成**——这就是"单周期 CPU"名字的由来。

如果你觉得这很复杂，请记住一件事：**这个数据通路是组合逻辑（除了 PC、寄存器堆、内存这三个有状态的部件）**。组合逻辑里所有信号同时流动，没有"先后"——所有 MUX 同时做选择，ALU 同时计算，加法器同时加。我们用"阶段"描述只是为了帮助理解，物理上整个通路在每个时钟周期内是同时活跃的。

### 五、控制单元：让数据通路做正确的事

数据通路只是搭好了"舞台"——它能做加法，能访问内存，能跳转。但**具体某个时钟周期到底要做哪件事，是由控制信号决定的**。比如 ALUSrc=0 让 ALU 第二输入选寄存器，ALUSrc=1 选立即数。所有这些控制信号合在一起，告诉数据通路"这一周期要执行什么样的指令"。

控制信号从哪里来？答案是**控制单元（Control Unit）**——一个组合逻辑电路，输入是当前指令的 opcode（以及部分 funct 字段），输出是所有控制信号。控制单元就是数据通路的"大脑"，它根据指令类型告诉每个 MUX 该怎么选、告诉 ALU 该做什么运算、告诉寄存器堆和数据存储器该不该写。

让我列出一个简化版的控制信号表。我们针对前面讨论的指令类型，列出每种指令需要什么样的控制信号组合：

```
指令类型      RegWrite  ALUSrc  MemRead  MemWrite  MemToReg  Branch  ALUOp
─────────────────────────────────────────────────────────────────────────
R 型 (add)     1         0       0        0         0         0      add
I 型 (addi)    1         1       0        0         0         0      add
load (lw)      1         1       1        0         1         0      add
store (sw)     0         1       0        1         X         0      add
分支 (beq)     0         0       0        0         X         1      sub
```

请仔细看这张表。每一行对应一种指令类型，每一列对应一个控制信号。"X"表示无关——比如 store 不写回寄存器，MemToReg 是什么都没关系。这张表实际上**完全定义了控制单元的行为**。控制单元就是一个把 opcode 翻译成这一行控制信号的查找表（或者等价的组合逻辑）。

我用 Verilog 风格的伪代码描述控制单元的核心逻辑：

```verilog
// 控制单元：根据 opcode 产生所有控制信号
module control_unit(
    input  [6:0] opcode,
    output reg   RegWrite,
    output reg   ALUSrc,
    output reg   MemRead,
    output reg   MemWrite,
    output reg   MemToReg,
    output reg   Branch,
    output reg [1:0] ALUOp
);
    always @(*) begin
        case (opcode)
            7'b0110011: begin  // R 型
                RegWrite = 1; ALUSrc = 0; MemRead = 0; MemWrite = 0;
                MemToReg = 0; Branch = 0; ALUOp = 2'b10;  // 看 funct 字段
            end
            7'b0010011: begin  // I 型算术 (addi 等)
                RegWrite = 1; ALUSrc = 1; MemRead = 0; MemWrite = 0;
                MemToReg = 0; Branch = 0; ALUOp = 2'b10;
            end
            7'b0000011: begin  // load (lw)
                RegWrite = 1; ALUSrc = 1; MemRead = 1; MemWrite = 0;
                MemToReg = 1; Branch = 0; ALUOp = 2'b00;  // 加法（算地址）
            end
            7'b0100011: begin  // store (sw)
                RegWrite = 0; ALUSrc = 1; MemRead = 0; MemWrite = 1;
                MemToReg = 1'bx; Branch = 0; ALUOp = 2'b00;  // 加法（算地址）
            end
            7'b1100011: begin  // 分支 (beq)
                RegWrite = 0; ALUSrc = 0; MemRead = 0; MemWrite = 0;
                MemToReg = 1'bx; Branch = 1; ALUOp = 2'b01;  // 减法（比较）
            end
            default: begin
                RegWrite = 0; ALUSrc = 0; MemRead = 0; MemWrite = 0;
                MemToReg = 0; Branch = 0; ALUOp = 2'b00;
            end
        endcase
    end
endmodule
```

ALUOp 是一个特殊的控制信号——它是"中间层"。控制单元不直接告诉 ALU 做什么具体运算（add、sub、and、or……），而是告诉一个叫 **ALU 控制器**的子模块大致的类别（比如"做算术运算，具体看 funct 字段"或"做减法用于比较"），ALU 控制器再结合指令的 funct 字段产生 ALU 的具体操作选择信号。这种"两级译码"的设计是为了应对 R 型指令的多样性——同样的 opcode 0110011 下，funct 字段可以指定 add、sub、and、or、xor、sll、srl 等多种运算。

### 六、一条指令的完整执行：把所有内容串起来

讲了这么多部件和信号，我用一条具体指令的执行过程把它们全部串起来。考虑这条指令：

asm

```asm
lw x10, 8(x11)
```

它的二进制编码是（我直接给出，不展开拆解过程）：

```
00000000 1000 01011 010 01010 0000011
imm[11:0]      rs1   f3   rd   opcode
```

opcode = `0000011`（load 指令族），funct3 = `010`（lw，32 位字加载），rs1 = 11，rd = 10，立即数 = 8。

让我们追踪它在单周期 CPU 中的执行过程。这一切都在**同一个时钟周期内同时发生**——但为了讲解清楚，我按因果顺序描述。

时钟上升沿 1 之前，PC 寄存器里存着这条 lw 指令的地址（假设是 0x1000）。时钟上升沿到来后（实际是上升沿之间，我这里描述的是周期内），整个数据通路开始活动。

PC 的输出 0x1000 同时送往两个地方：指令存储器（用于取指）和 PC+4 加法器（用于算下一条 PC）。指令存储器返回 0x1000 处的指令——也就是上面那条 32 位机器码。同时 PC+4 加法器算出 0x1004，等待最终被锁存。

指令的不同字段被并行送往各处。opcode = `0000011` 进入控制单元，控制单元（根据它内部的 case 语句）输出：RegWrite=1、ALUSrc=1、MemRead=1、MemWrite=0、MemToReg=1、Branch=0、ALUOp=00。这些信号瞬间传遍整个数据通路。

rs1 = 11 进入寄存器堆的读地址 1，寄存器堆输出 x11 的当前值（假设是 0x2000）。rs2 = 10 进入读地址 2——但 lw 不需要 rs2，这个值会被忽略（后续的 MUX 会选不到它）。立即数生成器看到这是一条 I 型指令（由 opcode 判断），从指令的高 12 位提取出立即数 0x008，并符号扩展为 32 位 0x00008。

ALU 的输入端：第一个输入是 x11 = 0x2000；第二个输入由 MUX 选择，因为 ALUSrc=1，MUX 选择立即数 0x00008。ALU 操作类型由 ALUOp=00 决定为加法，输出 0x2000 + 0x008 = 0x2008。这就是要访问的内存地址。

数据存储器收到地址 0x2008，因为 MemRead=1，它读出该地址处的 32 位数据（假设是 0x12345678）。

写回 MUX 收到三个候选输入：ALU 结果 0x2008、内存数据 0x12345678、PC+4 = 0x1004。因为 MemToReg=1，MUX 选择内存数据 0x12345678。这个值被送到寄存器堆的写数据端口。

PC 更新逻辑判断：因为 Branch=0，PC 更新 MUX 选择 PC+4 = 0x1004（不是 PC+offset）。

到这里所有信号都稳定了。**接下来时钟上升沿到来**——这个上升沿同时触发了三个时序部件的更新：寄存器堆把 0x12345678 写入 x10（因为 RegWrite=1）；PC 寄存器锁存 0x1004；数据存储器没有写入（因为 MemWrite=0），所以内存不变。

下一个时钟周期开始时，PC 已经指向下一条指令，x10 已经存了从内存读出的数据，CPU 开始执行下一条指令——重复这整个过程。

请你慢慢消化这个例子。它把这一讲所有的内容——五个阶段、各个部件、控制信号、组合逻辑与时序逻辑的配合——都浓缩在了一条指令的执行中。**当你能够在脑子里独立地走完任何一条指令的执行流程时，你就真正理解了 CPU**。

### 七、单周期 CPU 的根本缺陷

讲了这么久单周期 CPU 的优点（简单、清晰、易于理解），现在该谈谈它的根本缺陷了——**它太慢了**。

回到时钟周期的概念。一个时钟周期必须长到足够让最慢的指令在其内部完成。在我们的设计中，最慢的指令是哪条？是 load（lw）。为什么？因为 lw 在一个时钟周期内要依次（在组合逻辑中"依次"指信号传播路径）经过：指令存储器读取 → 寄存器堆读取 → ALU 运算 → 数据存储器读取 → 写回 MUX。这是最长的信号传播路径——叫做**关键路径（critical path）**。

假设各部件的延迟大致为：指令存储器 200 ps，寄存器堆读 100 ps，ALU 200 ps，数据存储器 200 ps，写回 MUX 50 ps。lw 指令的关键路径总延迟是 750 ps。所以时钟周期至少要 750 ps，时钟频率最高约 1.33 GHz。

但其他指令呢？R 型指令不需要访问数据存储器，它的关键路径只有 200+100+200+50=550 ps——本来 550 ps 就能做完。但因为时钟周期被定为 750 ps，**R 型指令也只能等到 750 ps 才能开始下一条**。这部分时间是被浪费的。

更糟的是分支指令——它甚至不写寄存器，关键路径只有 200+100+200=500 ps。结果同样要等 750 ps。

所以单周期 CPU 的根本问题是：**所有指令都被最慢的那条指令拖累**。在真实的程序中，load/store 指令大约只占 30%，但它们决定了所有指令的执行时间。剩下 70% 的指令都在浪费它们的"剩余时间"。

而且这只是组合逻辑的延迟。真实 CPU 中，主存访问要 100 纳秒——这意味着如果数据存储器真的接到主存，时钟周期要拉到 100 ns，时钟频率只有 10 MHz。这显然无法接受。

怎么办？两个互补的解决方案。**第一个**是上一讲已经讲过的——用缓存把"平均"内存访问时间拉到接近 L1 的速度。**第二个**就是下一讲要讲的——**流水线**。流水线的核心思想是：既然每条指令都要顺序经过五个阶段，何不让多条指令同时在不同阶段中流动？就像工厂的装配线：第一辆车在喷漆时，第二辆车在装轮胎，第三辆车在焊接车架——所有工位同时忙碌，每完成一道工序就有一辆车下线。CPU 也可以这样：第一条指令在写回时，第二条在访存，第三条在执行，第四条在译码，第五条在取指。理想情况下，每个时钟周期都有一条指令完成——吞吐量提高了 5 倍。

但流水线带来了新的麻烦：如果第二条指令依赖第一条的结果，但第一条还没写回怎么办？如果某条指令是分支，跳转的时候已经取了几条不该执行的指令怎么办？这些问题叫做**冒险（hazards）**，它们的处理是流水线设计的核心难题。这就是下一讲的主题。

### 八、本讲小结与下讲预告

我们这一讲走过了单周期 CPU 的完整设计：

我们从 CPU 工作的**五个阶段**开始——取指、译码、执行、访存、写回。这是任何指令执行都必须经过的概念性阶段，是后续所有 CPU 设计的骨架。然后我们列出了**关键部件**——PC、指令存储器、寄存器堆、ALU、数据存储器、立即数生成器、MUX。每个部件都有明确的功能，但它们的能力要靠合理的连接方式才能发挥。接着我们用**渐进的方式**构建数据通路——从 R 型开始，每加一种指令类型就在适当位置加一个 MUX，最终所有需求叠加形成完整的单周期数据通路。然后我们设计了**控制单元**——它是数据通路的大脑，根据 opcode 产生所有控制信号，让数据通路在不同指令下做不同的事。我们用一条 lw 指令的完整执行把所有内容串了起来。最后我们看到了单周期 CPU 的**根本缺陷**——所有指令被最慢的那条拖累，时钟周期被关键路径锁定。

我希望你从这一讲带走三个核心认识。第一个是**复杂的系统由简单部件组合而来**——一台 CPU 看似深不可测，但拆开来不过是几个寄存器、几个加法器、几个 MUX 加上一组连线规则。这种"复杂性从简单性涌现"的体验，是工程学习中最珍贵的时刻之一。第二个是**控制信号的力量**——同一套数据通路，不同的控制信号组合就让它执行完全不同的指令。这种"硬件灵活性来自配置"的思想，在 FPGA、可重构计算等更高级的领域反复出现。第三个是**理解一种设计的不足正是迈向下一种设计的开始**——单周期的低效性不是失败，而是理解流水线动机的最好铺垫。

下一讲我们进入**第六讲：流水线 CPU**。我们将看到如何让多条指令同时在不同阶段中流动，把吞吐量提高数倍；会理解流水线带来的三大冒险（结构冒险、数据冒险、控制冒险）以及对应的解决方案（前递、阻塞、分支预测）；会讨论流水线设计的工程权衡。这是计算机体系结构最经典也最迷人的章节，是从"能工作的 CPU"迈向"高性能 CPU"的关键一步。
