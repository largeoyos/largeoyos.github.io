# DCVC-RT：从“算多少”追到“为什么耗时”

依据：会议版 `DCVC-RT-CVPR2025.pdf` 的 §3、§4.2–4.5 与 Fig.3/4；固定版本 RT 编解码源码。相关流程另见总导读，本文集中分析设计动机与实验边界。

## FLOPs 和端到端时间之间有一段必须测量的距离

卷积计算量常随通道数近似平方变化；特征元素数则通常线性变化。若减少通道后，耗时没有按计算量比例下降，就说明存在其他瓶颈，不能仅靠 MACs 推断速度。

RT 区分计算成本、特征存取规模和模块调用数量。大的中间张量造成访存压力；很碎的计算增加启动、调度和同步开销。随着计算量降低，固定的调用成本可能变得更显著。因此它选择在低空间尺度保留较强处理能力，同时压缩高开销链路。

`pixel_unshuffle(8)` 先进行可逆重排，使主要特征网络在 1/8 尺度工作；主潜变量最终仍在 1/16。这个区别应从张量形状确认，而不是把论文中的 latent 一词在不同位置都当成同一张量。

## 隐式参考节省了一整条运动链路

RT 去掉显式光流估计、运动编解码和运动补偿分支，通过参考特征与当前内容的联合处理学习依赖。少一条链路意味着不只是少算卷积，还减少中间存储、调用与同步。

收益并非没有条件：大位移或遮挡可能更依赖明确对齐，场景切换则可能使显式运动失效。作者的分类消融提供这种取舍的证据；本轮只测试 Life，尚不能重复其分类结论。

## 概率模型与流水调度也属于架构设计

P 帧两阶段符号分组降低依赖深度，超先验、参考特征提取和 CPU rANS 的部分计算可通过流和事件安排重叠。融合算子则减少中间张量落地和重复调用。

因此单模块计时、GPU kernel 时间、真实包含熵编码的帧时延，以及包括读盘/评价的总任务时间，必须分别命名。多个任务并行后的吞吐也不是单帧延迟。后续性能实验应固定设备、线程、预热和同步范围，并明确是否包含码流写入。

## 不要把论文的部署选项自动当成当前环境事实

本轮 RT 脚本使用浮点 half 路径。离散符号用 int8 存储，不说明整网已经整数化。跨设备一致性需要在对应部署路径上独立核验，不能从一台 A100 的成功解码推出。

## 当前证据支持到哪里

这轮确实完成了六个 240 帧 RT 设置，检查了实际 QP、刷新标志、码流 bpp 和逐帧 PSNR。在首次有效刷新之前，对照轨迹完全相同；刷新之后差异逐渐扩大。这是状态传播对重建产生影响的直接实验线索。

但目前没有比较有/无光流的同训练消融，没有系统 profiler，也没有跨设备整数化验证。这些应保留为后续问题。下一项优先实验是不同刷新周期的完整 RD 与跨内容测试，先确认当前发现是否稳健，再讨论自适应策略。
